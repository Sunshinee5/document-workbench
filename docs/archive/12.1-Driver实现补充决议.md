## 二、B-01 Driver 生命周期（恢复 IExecutable）

评审正确。上一版为了强调 Driver 生命周期，把 `Execute` 丢掉了。

**正式冻结**：Driver 不是普通对象，它也是可执行组件，生命周期必须与冻结基线一致。

```
initialize()
execute()
cancel()
dispose()
```

**其它方法属于扩展接口，不是生命周期**：

```
health()
capabilities()
version()
```

即：`IDriver: IExecutable + IHealthCheck`，与现有代码一致，文档 12 第四节按此改写。

---

## 三、B-02 Task 参数归属（Task 自持业务参数）

评审抓到了真正的问题。**不是 DriverResult 的问题，也不是 ExecutionContext 的问题，而是「Task 的输入在哪里」。**

`ExecutionContext` 保存的是**运行环境**，不是业务参数。

例如旋转页面：`page = 5`、`rotation = 90` 不能放进 Context，否则 Context 会越来越大，8 字段冻结必然被撑破。

### 正式冻结：Task 自身保存业务参数

```
RotatePageTask {
    page,
    rotation,
}
```

`ExecutionContext` **仍然保持 8 字段，完全不增加**。

真正链路：

```
Command → build_tasks() → RotatePageTask(page=5) → execute(ctx)
```

Driver 拿的是 **Task 参数**，不是 Context。

### 删除 DriverResult

同意评审。统一使用 Rust 原生：

```rust
Result<T, DriverError>
```

不再搞 `DriverResult` + `Result` 双真值源。

## 四、B-03 DriverManager 不在执行链里

这条前几轮已经收束过，现在正式统一。

**执行链永远是**：

```
Command → Task → Driver → Runtime
```

**DriverManager 不是链上的一环**，它属于横切基础设施。

逻辑上，Task 执行时需要解析 Driver：

```
Task.execute() → DriverManager.resolve() → Driver.execute()
```

**但架构图以后全部改，不再画 DriverManager。** Manager 永远横切。

## 五、B-04 Driver 并发

这一条分两个问题。

### 第一：锁

评审说得对。如果 Manager 一直持锁，那么 Render 全部串行。

**正式冻结**：`DriverManager` 返回 `Arc<dyn Driver>`。Manager **只负责查找，不负责持锁整个生命周期**。这样 Render 可以并发。

### 第二：PDFium

见第八节技术路线冻结 —— PDFium 退出 Stage 2 阅读路径，转为后台能力。PDFium 的加载与绑定方式另行处理（`libloading` 运行时加载，因为项目是 GNU target，PDFium 官方只提供 MSVC `.lib`）。

## 八、Q1 技术路线冻结：Stage 2 查看全部走 PDF.js

**这是整个项目第一次真正的技术路线冻结。**

### 决定

**Stage 2 查看全部走 PDF.js。PDFium 退出 Stage 2 阅读路径，保留为后台能力。**

### 四条理由

**第一，项目定位。** 我们做的是 Document Workbench，不是 PDF 渲染器。用户最早需要的是「打开、滚动、搜索、缩放」，这些 PDF.js 全部成熟。

**第二，IPC 成本。** 如果 PDFium 渲染，每页都要 Bitmap 跨 IPC 传输。这是完全没必要的开销。React 天然适配 PDF.js。

**第三，PDFium 的真正价值不在 Viewer，而在后台。** 缩略图、打印、OCR 预处理、导出、高精度截图 —— 这些才是 PDFium 该做的事。

**第四，编辑仍然走 lopdf。**

### 正式冻结的分工

```
Stage 2 Viewer        → PDF.js
后台能力              → PDFium（Thumbnail / Print / Export / OCR）
编辑                  → lopdf
```

## 九、Q2 并发策略：Stage 2 冻结为串行

**不建议现在做并行。**

原因：MVP 阶段用户一次只看一页，没有几十页后台 Render 的需求。

**正式冻结**：

> Stage 2 的 Driver 允许串行。文档注明：「当前版本不启用后台并行 Render。」

到 Stage 4（缩略图、OCR、导出）再升级为 `Arc` + `Sync` + 线程池。

这样 Agent 不会为了未来的可能性，现在写一堆复杂锁。

## 十一、实现层必须澄清的两点（否则实现会跑偏）

以下是本决议落地到 Rust 时必然遇到的两个问题。裁定本身没写死，但实现只有一种写法能同时满足所有冻结条款，故在此明确。

### 11.1 Task 如何拿到 Driver：必须注入，不能让 Task 自己 resolve

决议第四节写「`Task.execute() → DriverManager.resolve() → Driver.execute()`」，这是**逻辑描述**，不是实现方式。

如果照字面实现成「Task 内部持有 `DriverManager` 引用并自己调用 resolve」，会产生两个问题：

1. Task 反向依赖 Manager，违反「Task 只是执行器、不调度」；
2. `Task` 是 `Box<dyn Task>`，要传 `DriverManager` 就得改 `IExecutable::execute` 的签名，而 `IExecutable` 是冻结的。

**唯一自洽的写法**是保持现有注入方式：

```rust
// TaskManager 负责 resolve，把 Driver 注入 Task
pub trait Task: IExecutable {
    fn required_capability(&self) -> Capability;
    fn task_name(&self) -> &str;

    /// 由 TaskManager 解析出 Driver 后注入
    fn execute_on(&self, context: &ExecutionContext<'_>, driver: &dyn IDriver) -> Result<(), DwError> {
        driver.execute(context)?;
        self.execute(context)
    }
}
```

这样同时满足：架构图上不出现 DriverManager（它只在 TaskManager 内部被调用）、Task 不依赖 Manager、`IExecutable` 签名不变。

### 11.2 Driver 如何拿 Task 参数：必须方法参数化，禁止接收 `&dyn Task`

决议第三节说「Driver 拿 Task 参数」，指的是**参数由 Task 提供**，不是**Driver 接收 Task 对象**。

如果实现成 `fn execute(&self, ctx: &ExecutionContext, task: &dyn Task)`，Driver 就反向依赖 Task 类型，分层彻底破掉。

**正确写法**：Driver 的能力方法接收具体参数，完全不认识 Task 的存在：

```rust
// Driver 侧：只认业务参数，不认识 Task
pub trait PdfEditor {
    fn rotate_page(&self, document: &Document, page: u32, rotation: i32) -> Result<(), DriverError>;
    fn delete_page(&self, document: &Document, page: u32) -> Result<(), DriverError>;
}

// Task 侧：自持参数，调用时传入
impl Task for RotatePageTask {
    fn execute_on(&self, context: &ExecutionContext<'_>, driver: &dyn IDriver) -> Result<(), DwError> {
        // 具体 Driver 由 shim 或 trait 分派拿到，这里示意
        driver.rotate_page(context.document, self.page, self.rotation)
    }
}
```

即：**参数从 Task 流向 Driver 的方法实参，不经过 Context，也不经过 Driver 对 Task 的依赖。**
