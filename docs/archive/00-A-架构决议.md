## 一、P0 冲突裁定

### P0-1 取消 PDFBox，禁止 Java 运行时

- 取消 Apache PDFBox，整个项目不允许引入 Java 运行时（JRE）。
- 原因：项目是 Rust + React + TypeScript，塞入 JRE 后绿色版体积大几十 MB，升级麻烦。
- 底层 PDF 对象操作统一改用 lopdf（Rust）。

### P0-2 Runtime 只管运行环境

- Runtime 仅管理运行环境，不含第三方库。
- Runtime 组成：Fonts、Language、Cache、Temp、Logs、Config、Workspace。
- 第三方（如 PDFium）属于 Engine，不属于 Runtime。
- 分工：Engine 调用第三方，Runtime 管理运行环境。

### P0-3 Snapshot 改为 Command · Diff · Checkpoint 三层

- 采用三层结构：Command（记录增量）→ Diff → Checkpoint（完整状态）。
- Command 只记录最小增量，例如 DeletePage 只记 Page 5，不记整个 PDF。
- 每累积 100 条 Command 自动生成一个 Checkpoint（完整 Document）。
- Undo 从 Checkpoint 恢复，不再回放 1000 条命令。
- Snapshot 不是每一步都做，Checkpoint 才是完整快照。
- 开发文档 04 的 Snapshot 部分待按此重写。

### P0-4 Document 不改名，增加 ViewModel

- 不采纳 DocumentModel 命名。Workspace 里保存的就是 Document。
- 理由：Adobe、Office 都称 Document；MVVM 中 Document 仍是 Document。
- 只增加 DocumentViewModel 一层，Document 本身不改。
- 正式 MVVM 链路：UI → ViewModel → Command → Service → Engine。

## 二、其余冲突裁定

### Service 与 Command

- 统一链路：UI → Command → Service → Engine。
- Command 绝不能写业务逻辑，只做转发。
- 示例：DeletePageCommand 内部只有 `Service.deletePage()`；真正的删页逻辑全部在 Service。

### History 重新设计为两个

- WorkspaceHistory：负责整个工作台的操作记录，例如打开、关闭、切换、打印。
- DocumentHistory：负责当前 Document 的 Undo / Redo。
- 取消 HistoryService。

### MVVM

- 增加 ViewModel 层，正式采用 MVVM（此前五层里没有 ViewModel）。

### Plugin 第一版即按契约实现

- OCR 第一版不直接调 OCRService，而是 OCRPlugin → PluginManager → OCR Engine。
- PluginManager 默认加载内置插件。
- 以后开放外部 dll 时无需重构。

### PDF 三个库边界

- PDF.js → Viewer（阅读界面）
- PDFium → Render（渲染）
- lopdf → Object（底层对象操作）
- pdf-lib 取消，原因：功能重复。

### OCRmyPDF

- Windows 落地情况重新调研。
- 若 Windows 支持不好，第一版直接采用 PaddleOCR + Tesseract，不使用 OCRmyPDF。

### 多语言

- 第一版只有 zh_CN。
- lang 目录保留，但里面只有一个语言包。
- 不做 Language 选择功能。

### PDF 转 Word 验收

- 增加测试集：合同、论文、发票、说明书、表格、扫描件。
- 为每类定义明确的通过标准。

### 目录结构

- 全部以开发文档 03 为准统一。开发文档 01 第七节的目录作废。

## 三、架构升级决定

> **后续覆盖说明**：本章作于 Capability 架构之前。开发文档 05 已把项目从 Engine 架构整体升级为 Capability 架构，最终链路为 UI → ViewModel → Command → Service → Capability → Provider → Runtime；Session 与 Workspace 顺延至第 08 章。本文件第一、二节的裁定仍然有效（禁 Java、Runtime 定义、MVVM、History 二分、Command 转发、Plugin 契约等），但凡出现 "Engine" 字样处，均理解为由 Capability + Provider 取代。冲突时以文档 05 为准。

原第五章计划写 Command，现改为：

**第五章：《Document Session（文档会话）架构》**

原因：Command、History、Snapshot、Selection、Clipboard 本质上都属于一次"文档编辑会话"的状态。Session 定义清楚后，Command、Undo/Redo、AI、插件都会自然落位，不需要后面再修架构。

拟议结构：

```
Session
├── Document
├── Workspace
├── History
├── Selection
├── Clipboard
├── Snapshot
└── Command
```

打开一个 PDF，实际打开的是一个 Session。以后 AI、OCR、插件、宏全部基于 Session。

目标：更接近 VS Code、JetBrains 等现代 IDE 与专业桌面软件的架构。

## 四、待澄清（整理者标注，非用户裁定）

以下问题由理解过程中发现，需用户在后续章节或讨论中定夺，整理者不擅自修改裁定：

1. **决议内部不一致**：P0-1 段落保留 pdf-lib 作"浏览器对象修改"，后文"PDF 三个库边界"又取消 pdf-lib。按时间顺序以后者为准（已按取消记录），请确认。（文档 05 已明确 PDF 作为 Provider 实现，PDFium 作 Render Provider。）
2. **lopdf 能力边界**：lopdf 偏底层对象读写，Merge/Split 可胜任，但原 PDFBox 承担的 Form、Sign、Encrypt、Bookmark 等能力 lopdf 未必覆盖，需要单独确认替代方案。
3. **Session 上帝对象风险**：Session 囊括 Document/Workspace/History/Selection/Clipboard/Snapshot/Command 七类对象，需明确 Session 是"持有引用的协调者"还是"内联实现的大对象"，避免违反单一职责。
4. **Checkpoint 存储成本**：100 条 Command 生成一个完整 Document 快照，对几百 MB 的大 PDF 成本高。需明确 Checkpoint 存内存还是磁盘、保留几份、是否压缩。
5. **Command 空壳化**：Command 只转发 Service 时，其存在价值需明确（撤销元数据、权限、日志、AI 入口都应挂在 Command 基类上），否则会生成一堆空壳类。
6. **跨文档 Undo 归属**：合并两个 PDF 这类跨文档操作，Undo 应记入 WorkspaceHistory 还是 DocumentHistory，边界未定。
7. **History 与 Service 层定位**：取消 HistoryService 后，History 逻辑落到 Workspace/Document 对象里，而文档 03 强调 Service 层"网上没人做但必须有"，需确认 Service 层是否因此被削薄。
8. **PluginManager 与 Service 关系**：OCRPlugin → PluginManager → OCR Engine，Service 层如何与 PluginManager 衔接（Service 调插件，还是插件即 Service）未定义。
9. **ViewModel 引入后的 State 表述**：文档 04 说"UI 看 State"，增加 ViewModel 后应改为"ViewModel 看 State、UI 只看 ViewModel"，需同步。
10. **PaddleOCR 体积**：PaddleOCR 的推理库与模型文件在 Windows 上并不小，与"轻量化"目标仍有张力，需在调研中一并评估。
