## 一、执行链冲突（立即修正）

这是文档错误，不是架构错误。以第十四节为准。

以后唯一合法执行链：

```
UI
↓
ViewModel
↓
Action
↓
Command
↓
Task
↓
Driver
↓
Runtime
```

Capability 退出执行链。基线第一节已全部修改。以后 Agent 只认这一张图。

## 二、Manager 是否属于执行链

正式定义：Manager 不是执行层，属于横切基础设施。

例如 Command → Task，Task 执行，TaskManager 只是调度。TaskManager 负责创建、暂停、恢复、取消、依赖分析、优先级，它不处理业务。

所以执行链仍然只有 Action → Command → Task → Driver → Runtime。Manager 属于横切基础设施，不进入执行链。

## 三、生命周期统一

拆成基类 + 扩展接口，统一但不丢能力。

基类 `IExecutable`：

```
Initialize()
Execute()
Cancel()
Dispose()
```

扩展接口：

- Task：`IPausable` → Pause()、Resume()
- Driver：`IHealthCheck` → Health()、Version()

统一，但不丢能力。

## 四、Checkpoint（正式冻结）

今天最重要的一条。以后 Undo 分两层：

1. **语义层：Command**。例如 DeletePageCommand 负责记录 Undo。
2. **存储层：Checkpoint**。负责恢复。

```
Command → Diff → Checkpoint
恢复：Checkpoint + 后续 Diff → 当前状态
```

Command 是真值源，Checkpoint 只是优化。以后 Agent 不要混。

## 五、Execution Graph 定位（08 章前置）

正式冻结：Execution Graph 不是新层，不是新架构，只是 TaskManager 内部的数据结构。

```
TaskManager → ExecutionGraph(DAG) → Task
```

以后架构图不会增加 ExecutionGraph，它只是 TaskManager 的实现。这一条会写进 08 章第一节。

## 六、HistoryService（正式取消）

Agent 发现冲突，采纳。以后取消 HistoryService。

- History 属于 Session。
- Undo 属于 Command。
- Checkpoint 属于 Session。
- Service 以后不要 History。

## 七、Office、OCR、Cloud 等问题

这些全部属于 MVP 实现，不是架构，所以不进入冻结基线。以后单独建立《MVP Implementation Decision》文档，在里面确定，例如：

- PDF：PDFium
- OCR：Windows OCR（默认）+ Tesseract（可选）+ Paddle（插件）
- Office：LibreOffice（默认）+ ONLYOFFICE（实验）
- 联网：默认关闭
- 图片转 PDF：属于 ExportCapability，不属于图片 Convert

这样架构和实现彻底分离。

## 八、禁止"概念驱动开发"（最后一条）

这是这几天最大的教训。以后任何新想法必须回答三个问题：

1. 现有架构真的解决不了吗？
2. 新增的是新能力，还是已有能力的实现？
3. 有没有减少复杂度？

只有三个都满足才能新增，否则禁止。

## 九、Capability Gate Principle（后续追加决议）

> 追加时间：2026年11月22日。用户正式拍板 Capability 校验时机，作为第 08 章第一条原则写入。

Capability 不参与执行，只参与 Task 创建之前的合法性校验。

执行流程：

```
Action → Command → TaskManager → Capability Check → Task → Driver → Runtime
```

规则：

- TaskManager 在 ExecutionContext 上统一调用 `HasCapability(...)`。
- 校验为 true：创建 OCRTask 等具体 Task，进入调度队列。
- 校验为 false：抛出 `CapabilityNotSupported` / `TaskRejected`，Task 根本不会创建。
- Capability 永远不进入 Runtime，只是 Task 的准入条件（Gate），不是执行者。
- ExecutionContext 是 Task 执行期临时上下文（不是 Session 成员），持有 Session / Document / Workspace / Selection 的 Reference（借用，不按值拥有），并按值持有 CapabilitySet、Config、Progress、CancelToken；字段严格固定为 8 个，禁止新增。
- Task 不再判断能力，Driver 更不判断——整个链路只有一次检查。

**Capability Gate Principle**：所有 Task 在进入调度队列之前，必须经过 Capability Gate 校验。AI、插件、宏、批处理全部走同一套 Gate。

## 最终决定

从这一刻开始，架构阶段结束。后面的文档不再新增核心层、不再新增 Manager、不再新增 Context、不再新增生命周期。08 开始全部进入实现设计：

- 08：TaskManager 如何实现 DAG、依赖、并发、失败重试
- 09：Session 的内部数据结构、Checkpoint、恢复机制
- 10：Workspace 的组织方式
- 11：Command 的注册、撤销、重做
- 12：Driver 的发现、加载、隔离

从现在开始讨论的是"怎么实现"，而不是"再发明一个新概念"。这是整个项目真正可以开始编码的起点。
