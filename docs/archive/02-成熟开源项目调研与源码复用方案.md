# Document Workbench 开发文档 02

> **注意：本章部分条款已被 `00-A-架构决议.md` 修正，冲突时以决议为准。**
> 受影响条款：取消 PDFBox（Java 生态，禁用 JRE）；pdf-lib 取消（功能重复）；PDF 库最终边界为 PDF.js → Viewer、PDFium → Render、lopdf → Object；Runtime 只管运行环境，第三方（PDFium 等）归 Engine 调用；OCRmyPDF 待重调研。

## 成熟开源项目调研与源码复用方案

### 一、项目筛选原则

| 条件 | 要求 |
|------|------|
| GitHub 活跃 | 最近一年持续更新 |
| License | 优先 MIT / Apache-2.0 / BSD；谨慎使用 GPL / AGPL |
| Windows | 必须支持 |
| 可长期维护 | 社区活跃 |
| 可替换 | 不与业务强耦合 |
| 可封装 | 不直接修改源码，优先封装 |

原则：Fork 越少越好，封装越多越好。

### 二、整个项目建议采用的成熟项目

**第一层：PDF 查看 — PDF.js（Mozilla）推荐指数 ★★★★★**

作用：PDF 阅读、文本层、搜索、目录、缩略图、复制、缩放、打印。

建议：不修改核心源码，只封装 Viewer，新增 Workspace、Ribbon、右键菜单、快捷键。

保留：viewer/、web/、TextLayer、AnnotationLayer、Thumbnail、SearchController、Bookmark、History。

不要：修改 Canvas、渲染器、解析器。否则以后升级几乎不可能。

**第二层：PDF 底层 — PDFium（Google）推荐指数 ★★★★★**

作用：Render、Font、Object、Image、Page、Memory。这是 Chromium 使用的 PDF 引擎，业内最成熟的 PDF 渲染内核之一。

不要 Fork，不要修改。采用封装，升级直接替换版本。

**第三层：PDF 对象处理 — Apache PDFBox 推荐指数 ★★★★★**

作用：Merge、Split、Metadata、Encrypt、Form、Sign、Bookmark。

优点：Java 生态非常成熟，很多 PDF 操作比浏览器端库更稳定。只调用，不改源码。

**第四层：Office 转换（特别注意）**

很多项目自己解析 DOCX，这是错误路线。建议采用成熟 Office 转换能力作为第一阶段实现，以后需要替换时通过统一接口切换不同实现。

**第五层：OCR**

第一阶段 OCRmyPDF + Tesseract，第二阶段增加 PaddleOCR。不要自己写 OCR。

### 六、压缩

不要自己实现。采用 qpdf、Ghostscript。调用，不要 Fork。

### 七、图片

不要自己写。采用 ImageMagick 或 GraphicsMagick。以后所有图片全部统一。

### 八、哪些项目值得参考 UI（不是 Fork，而是参考）

- Adobe Acrobat：Ribbon、右侧工具栏、最近文件、标签。不要照搬。
- WPS PDF：Office 风格、文档标签、最近、收藏。
- PDFgear：首页、功能分类、工具箱。
- PDF-XChange：专业工具布局、右键、状态栏。
- ONLYOFFICE：Office 布局、主题、工作区。

### 九、不建议直接 Fork 的项目

- PDF Sam：适合工具箱，不适合 Workbench。
- PDF Arranger：GTK，不适合现代 UI。
- SumatraPDF：非常优秀，但是阅读器不是 Workbench。可以借鉴启动速度、缓存，不要 Fork。

### 十、建议 Fork 的项目

只有一个：Stirling PDF Desktop（选择性借鉴）。

不是 Fork 整个项目，而是学习 Desktop、国际化、Task、Pipeline、API、桌面打包、工具封装。

不要保留 Server、Docker、登录、企业版、Web 部署、收费模块。把它当作能力来源，不要当作最终产品。

### 十一、License（必须遵守）

| 类型 | 建议 |
|------|------|
| MIT | ✅ 可直接复用 |
| Apache-2.0 | ✅ 推荐 |
| BSD | ✅ 推荐 |
| LGPL | ⚠️ 动态链接优先，不修改源码 |
| MPL | ⚠️ 可用，但修改相关文件需公开 |
| GPL | ⚠️ 谨慎，可能要求整体开源 |
| AGPL | ❌ 第一阶段尽量避免作为核心依赖 |

不要因为一个功能，把整个项目许可证变复杂。

### 十二、统一封装原则

以后所有第三方统一放在 Engine/ 下：

```
engine/
├── pdf/
├── office/
├── ocr/
├── image/
└── compress/
```

UI 绝不能直接调用第三方，全部走 Engine。这样以后替换 PDFium 只需要改 Engine。

### 十三、不要直接修改第三方源码

以后升级采用：Git Pull → 重新编译 → 测试。

如果改第三方源码，以后升级基本废了。原则：能封装就封装，不能封装再评估是否 Fork。

### 十四、第一阶段建议最终组合

```
UI
├── React
├── TypeScript
└── Tauri

Engine
├── PDF.js（阅读）
├── PDFium（渲染）
├── PDFBox（PDF 操作）
├── Office Adapter（转换）
├── OCR Adapter
├── qpdf
├── Ghostscript
└── Image Adapter

Workspace
Plugin
Config
```

### 十五、本章验收标准

- 建立统一 engine 层。
- 明确第三方库边界，不让 UI 直接依赖底层。
- 建立统一接口（PDF、Office、OCR、Image、Compress）。
- 梳理所有许可证，避免未来因 License 影响发布。
- 保证第三方依赖可升级、可替换。

### 优化建议（准备放到第三章）

不是告诉 Agent 用什么，而是告诉 Agent 每个成熟项目里哪些源码值得直接学习、哪些架构思想值得迁移、哪些代码不要碰。例如：

- PDF.js：重点学习 TextLayer、搜索索引、虚拟滚动，而不是修改渲染器。
- Tauri：学习 IPC、文件系统权限和自动更新，而不是改运行时。
- Stirling：学习任务流水线（Pipeline）、工具注册方式，而不是照搬整个项目。
- qpdf：只调用命令或库接口，不修改底层算法。
- PDFium：作为渲染引擎封装，不侵入其内部实现。

这样 Agent 不仅知道用什么，还知道怎么用、为什么这么用。
