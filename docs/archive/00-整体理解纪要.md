## 一句话本质

这不是一个 PDF 工具，而是以工作台为主体、把文档能力做成可插拔能力的本地框架。PDF 只是第一个用来验证架构成立的能力，真正要护住的是 Document / Command / Workspace / Engine 这套结构，而不是某个 PDF 功能。

## 四章的递进关系

- 01 定边界：是什么、不做什么、验收什么。最有价值的是"明确不做"清单，它决定了 Agent 不会跑偏去碰 AI/云/账号。
- 02 定选型：用什么、不用什么、License 红线。核心纪律是"封装不 Fork、不造轮子、UI 不直接碰第三方"。
- 03 定结构：代码放哪、按什么顺序写。把前两章落到五层架构 + 统一 Document + Command/History + 自下而上的开发顺序。
- 04 定模型：Document 数据模型。把 03 里"统一 Document"这一句话展开成可落地的对象设计——状态机、脏标记、选择集、剪贴板、元数据、权限、快照、历史、标签、Engine 绑定、缓存归属。

四章是 战略 → 战术 → 结构 → 模型，始终重复同一组词：可替换、可封装、可扩展。

## 贯穿四章的铁律

1. 工作台是主体，PDF 只是能力之一。
2. 边界即纪律：UI 只显示不解析，Engine 隔离第三方，禁止跨层调用。
3. 先找成熟方案，最后才允许自己写；能封装就封装，改源码等于放弃升级。
4. 扩展点现在就按契约实现（决议更新）：Plugin 第一版即走 OCRPlugin → PluginManager → OCR Engine，只是默认加载内置插件；Command 只转发不写业务；History 拆为 WorkspaceHistory 与 DocumentHistory。
5. 自下而上开发：Runtime → Engine → Service → Workspace → UI，先立骨架。
6. 多态替代条件判断：禁止 if(pdf) / if(word) / if(image)，统一走 Document 抽象。
7. 正式 MVVM（决议新增）：UI → ViewModel → Command → Service → Engine。
8. 禁用 Java 运行时（决议新增）：取消 PDFBox 与 pdf-lib，PDF 底层改用 lopdf。

## 第 04 章新增理解要点

1. 统一 Document + 继承：基类只放公共属性，格式特有字段下沉到子类（PDF 的 PageCount/Outline/Form，Word 的 Paragraph/Style/Section），避免基类被某一格式污染。
2. 生命周期统一：Create → Open → Load → Ready → Edit → Modified → Save → Export → Close → Dispose，所有格式一致，Agent 不重复开发。
3. State 驱动 UI：Loading/Ready/Editing/Saving/Exporting/OCR/Converting/Printing/Closed。按钮灰掉等交互由 State 决定，UI 不自己判断业务状态。
4. Dirty 与 Checkpoint 分工（决议更新）：Dirty 负责"关窗是否提示保存"的统一判定；撤销改为 Command · Diff · Checkpoint 三层——Command 只记增量（如 Page 5），每 100 条 Command 生成一个完整 Document 的 Checkpoint，Undo 从 Checkpoint 恢复而非逐步回放。原 Snapshot 逐步快照方案作废。
5. Selection / Clipboard / Metadata / Permission / Tag 全部做成全局统一对象，为 AI、OCR、跨文档复制、右键菜单、工作区分类提供统一入口。
6. Engine 绑定：Document 依据 type 绑定对应 Engine，彻底消灭 if-else 分支。
7. 缓存归属：Thumbnail、Preview、Render、OCR、SearchIndex 由 Document 自己管理，不散落各处。
8. 真正价值：这一章决定 AI、插件、OCR、历史能否统一，是"以后几乎不用重复开发"的地基。

## 第 05 章：Capability 架构（架构分水岭）

这是整个项目最大的一次升级。前四章按"文件类型"拆 Engine（PDF/Office/OCR Engine），第 05 章推翻它，改为按"能力"抽象。

- **为什么**：Word 和 PDF 都需要 Render/Print/OCR/Search/Export，按格式拆会重复且无限膨胀（CAD 呢？EPUB 呢？）。
- **核心**：Document 组合 Capability[]；用 `HasCapability(Render)` 替代 `if(pdf)`；AI 问的是"有没有 OCR"而非"是不是 PDF"。
- **四件套**：CapabilityManager（统一调度）、CapabilityRegistry（注册 + Version/Priority 自动选 Provider）、CapabilityContext（Document/Workspace/Selection/Session/Progress/CancelToken 统一入参）、ICapability（Initialize/CanExecute/Execute/Dispose）。
- **Provider**：Capability 不自己实现，交给 Provider。OCR 可切 Paddle/Tesseract，Convert 可切 LibreOffice/OnlyOffice/Cloud，切换不改 Capability。
- **Plugin 重新定义**：插件不是注册菜单，而是注册 Capability。
- **Session 重新定义**：只保存状态（Document/Workspace/Selection/Clipboard/History/Command/Snapshot/CapabilityContext），绝不处理业务。
- **最终 V2 链路**：UI → ViewModel → Command → Service → Capability → Provider → Runtime，Session 贯穿。
- **开发原则**：新增功能先问"是新文件类型还是新能力"。加 EPUB 不是加 EPUBEngine，而是声明 EPUB → Render/Search/Print。

后续章节已调整：06 Provider、07 Command+Transaction+Undo/Redo、08 Session+Workspace、09 Document Pipeline、10 UI 与 Workbench，最后单独写《PDF Provider 实现》。PDF 从架构中心降为第一个 Provider。

## 架构冻结基线 00-B（当前唯一有效架构）

用户已采纳前七章的问题反馈，发布冻结基线，禁止后续新增核心层。冻结要点：

- **执行链（唯一）**：Action → Command → Task → Driver → Runtime。
- **退出执行链**：Service（横切业务）、Session（共享状态）、Capability（静态能力声明 HasXXX）、Strategy（取消，改为 Task 参数）。
- **三个 Manager**：DriverManager / TaskManager / SessionManager，禁止新增。
- **一个 Context**：ExecutionContext（随 Task 创建/释放的临时上下文，非 Session 成员；Session/Document/Workspace/Selection 以引用持有，CapabilitySet/Config/Progress/CancelToken 按值持有，字段严格固定 8 个）。
- **一套生命周期**：Initialize / Execute / Cancel / Dispose。
- **Undo 唯一真值源**：Command，Task 绝不记录 Undo、不存历史、不做快照。
- **AI 唯一身份**：Command Generator，禁止直接调 Runtime、禁止 AI Driver。
- **冻结令**：08–20 章禁止新增核心层，除非证明现有架构解决不了。

基线包含 10 条待澄清，重点是第一节链路与冻结系统图不一致、Manager 是否在链中、Checkpoint 存废、Pipeline 定位、HistoryService 存废。

## 补充决议 V1.1：架构阶段结束

用户已采纳并裁定基线全部 10 条待澄清，发布 V1.1：

1. **执行链冲突修正**：系文档错误，以第十四节为准，唯一合法链为 UI → ViewModel → Action → Command → Task → Driver → Runtime；Capability 退出，基线第一节已改。
2. **Manager 非执行层**：属横切基础设施，只调度不处理业务，不进执行链。
3. **生命周期拆基类 + 扩展**：`IExecutable`（Initialize/Execute/Cancel/Dispose）+ `IPausable`（Task）+ `IHealthCheck`（Driver），统一但不丢能力。
4. **Checkpoint 正式冻结**：Undo 两层——语义层 Command（真值源，记 Undo）+ 存储层 Checkpoint（优化恢复）；恢复 = Checkpoint + 后续 Diff。
5. **Execution Graph 定位**：非新层，是 TaskManager 内部 DAG 数据结构，08 章第一节写明。
6. **HistoryService 取消**：History 与 Checkpoint 属 Session，Undo 属 Command。
7. **实现问题分离**：Office/OCR/Cloud 等归入 `00-C-MVP实现决策.md`，不进架构基线。
8. **禁止概念驱动开发**：新想法须过三问（现有架构真解决不了？是新能力还是已有实现？是否减少复杂度？），全满足才准新增。

**最终决定**：架构阶段结束。08 起为实现设计（08 TaskManager DAG/并发/重试、09 Session/Checkpoint、10 Workspace、11 Command、12 Driver），不再新增核心层/Manager/Context/生命周期。这是项目可以开始编码的起点。

## 第 09 章：Session 架构 + 章节顺序调整

用户调整实现设计顺序：08 Execution Graph → 09 Session → 10 Workspace → 11 Command/Undo/Checkpoint → 12 Driver 加载。理由：Workspace 只是 Session 的成员，先写 Workspace 会导致 Session 返工。

第 09 章要点（实现设计，不新增核心层）：

- Session 是一次文档工作会话，只维护状态（CurrentDocument/Workspace/Selection/Clipboard/HistoryIndex/Checkpoint/Configuration/TemporaryData），禁止调 Driver/Runtime、修改文档、执行业务、调度 Task；ExecutionContext 不是 Session 成员，由 TaskManager 在 Task 创建时临时构造。
- 生命周期 Create → Initialize → Running → Closing → Disposed；关闭时释放 Driver/Task 引用、临时缓存、Checkpoint。
- 唯一 SessionManager（创建/关闭/切换/查询，不处理业务）；多文档会话彼此隔离，禁止共享 History/Selection/Checkpoint。
- ExecutionContext 是 Task 创建前由 TaskManager 临时构造的统一上下文（非 Session 成员，持有 Session/Document/Workspace/Selection 引用），随 Task 结束释放；Capability Gate 在此统一校验（呼应 V1.1 第九条）。
- Checkpoint 属于 Session：Command → Diff → Checkpoint，每 100 条生成，优先落盘、内存仅留最近一个。
- Selection/Clipboard 属 Session；Workspace 属 Session 且不反向持有；Driver 生命周期归 DriverManager、Session 只存状态引用；Task 由 TaskManager 创建、Session 只存状态引用。
- 持久化只存最近文件/布局/缩放/当前页/主题/配置，不存 Task/Driver/Runtime；Recovery/session.json 支持恢复。
- 目录 Core/Session/{Session,SessionManager,CheckpointManager,Recovery}（ExecutionContext 非 Session 成员，不列入该目录，由 TaskManager 在 Task 创建时构造）。

**发现的问题见项目 MEMORY**：技术栈冲突（CMake/Qt/C++ vs Tauri/React/Rust）、SessionManager 与 V1.1 冻结 Manager 关系、CheckpointManager 与"HistoryService 取消"的命名一致性、ExecutionContext 字段与基线差异等。

## 技术栈冻结 00-D（开工前置条件已解除）

用户采纳决策分析，确认 CMake/Qt 仅为举例笔误，正式撤销。唯一技术栈：React + TS + Vite（UI）/ Tauri 2.x（Desktop）/ Rust（Core）/ PDFium + lopdf（PDF）/ Windows OCR 优先 + Tesseract 可选 + Paddle 插件（OCR）/ LibreOffice 默认 + ONLYOFFICE 后续（Office）/ Cargo Workspace + pnpm + Vite（Build）。禁止 Qt、CMake、C++ Runtime。AI 维护 Rust 比 Qt C++ 更容易（错误确定、生命周期明确、Cargo 统一、训练数据多）。全部 Task 用 Rust trait 实现 `impl Task for RotateTask`。

同时采纳 09 章四条修正：CheckpointManager → CheckpointStore；ExecutionContext 唯一字段固定禁增；Session 生命周期属状态生命周期不属 IExecutable；多 Session 多 Recovery。
