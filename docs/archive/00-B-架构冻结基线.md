# Document Workbench 架构冻结基线（Architecture Baseline）

Version 1.0 + 补充决议 V1.1

本文档优先级最高，高于 01–07 所有章节，也高于 `00-A-架构决议.md`。

**补充决议 V1.1（见 `00-B-补充决议V1.1.md`）已裁定本文全部待澄清项，并修正了第一节执行链。V1.1 与本文冲突时以 V1.1 为准。**

从本基线开始，架构层禁止新增概念。后续章节只能实现、细化或扩展，不允许再创造新的核心层级。

**架构阶段已于 V1.1 宣布结束，08 章起全部为实现设计。**

## 一、架构冻结原则

以后任何新的设计，先问：是不是已有层能解决？如果能，禁止新增。

例如以后不能再出现：ExecutionManager、WorkflowManager、CapabilityExecutor、DriverExecutor、PipelineManager，全部禁止。

**唯一合法执行链（V1.1 修正，以第十四节冻结系统图为准）：**

```
UI
↓
ViewModel
↓
Action
↓
Command
↓
Task
↓
Driver
↓
Runtime
```

Capability 退出执行链。Agent 只认这一张图。

## 二、Service 重新定位（重要）

这是 Agent 指出的最关键的问题。

以前 Service 是一层，现在修改：Service 不是一层，Service 属于横切业务。

例如 DocumentService、WorkspaceService、HistoryService、PluginService，它们不属于执行链，只是业务组织。

```
Command → DocumentService → Task
```
或
```
WorkspaceService → Command
```
都允许。

所以 Service 退出主架构，以后架构图不画 Service。

## 三、Session 重新定位

Session 也不是执行层，Session 属于上下文，贯穿整个执行链。

```
Action → Command → Task → Capability → Driver → Runtime
```

全部共享 Session。

## 四、Strategy 取消

Agent 指出 Strategy 悬空，采纳。以后取消 Strategy。

为什么？例如 OCR 的快速、高精度，其实应该属于 Task 参数：

```
OCRTask.mode = Fast
```

不是一层。以后禁止 Strategy。

## 五、Manager 统一

这是 Agent 指出的第二个非常重要的问题。

以后整个项目只有三个 Manager：

1. **DriverManager**：负责 Driver。
2. **TaskManager**：负责 Task。
3. **SessionManager**：负责 Session。

除此之外禁止新增 Manager，例如 CapabilityManager、WorkflowManager 全部取消。

## 六、Context 统一

以前 CapabilityContext、DriverContext、TaskContext 全部取消。

以后统一为 `ExecutionContext`，字段严格固定 8 个：Session、Document、Workspace、Selection 以 Reference（引用）持有，CapabilitySet、Config、Progress、CancelToken 按值持有。它是随 Task 创建/释放的临时上下文，不是 Session 成员。以后 Agent 禁止新增 Context。

## 七、生命周期统一

以后 Capability、Task、Driver 统一一个生命周期：

```
Initialize()
Execute()
Cancel()
Dispose()
```

不要三套。

## 八、Undo 真值源（正式冻结）

这是最重要的一条。

以后整个项目只有一个真值源，就是 Command。

```
RotateCommand 记录 Undo
```

Task 绝不能记录 Undo，Task 只是执行。

```
RotateCommand → RotateTask
```

Undo 永远回滚 Command，不是 Task。

## 九、Task 职责重新定义

Task 以后只是执行器：

```
RotateTask → Driver
```

Task 禁止保存历史、禁止 Undo、禁止快照、禁止业务。

## 十、Capability 职责重新定义

Capability 不是执行，Capability 只是能力声明：

```
Document → HasOCR / HasRender / HasSearch
```

真正执行的是 Task，不是 Capability。

## 十一、AI 定位（正式冻结）

Agent 指出 AI 三种身份，以后正式统一。

AI 只有一个身份：**Command Generator（命令生成者）**。

```
用户："翻译整个 PDF" → AI → Generate Commands → Task → Driver
```

AI 以后禁止直接调用 Runtime，禁止 AI Driver。

## 十二、执行链（最终冻结）

整个系统以后只有这一条：

```
Action → Command → Task → Driver → Runtime
```

Capability 作为静态能力描述，Session 作为共享状态，Service 作为横切业务，都不属于执行链。

## 十三、为什么 Capability 退出执行链

这是今天最大的修改。

以前写 `Command → Capability → Driver`，现在取消。

原因：Capability 不执行。`HasCapability(OCR)` 只是判断，真正执行的是 `OCRTask → OCRDriver`。

以后 Capability 不再参与执行。

## 十四、最终系统图（冻结版）

```
                   UI
                    │
               ViewModel
                    │
                 Action
                    │
                Command
                    │
              +-------------+
              | TaskManager |
              +-------------+
                    │
                  Task
                    │
             DriverManager
                    │
                 Driver
                    │
                 Runtime

横向：Session、ExecutionContext、Capability、Service 共同支持，不进入执行链。
```

## 十五、禁止继续新增概念

从这一章开始，后续 08–20 禁止新增新的核心层。

如果确实需要新增，必须证明现有架构解决不了，否则 Agent 拒绝接受。

## 待澄清（整理者标注，非用户裁定）

1. **第一节链路与冻结系统图不一致**：第一节仍写 `… → Task → Capability → Driver → Runtime`（Capability 在执行链中），但第十二、十三节明确 Capability 退出执行链，第十四节系统图也不含 Capability。本文按第十四节记录为唯一有效版本，请确认并修订第一节。
2. **Manager 是否进入执行链**：第五节定义三个 Manager 为管理者，但第十四节系统图把 TaskManager、DriverManager 画在执行链中间的节点位置。需明确 Manager 是"调度者（横切）"还是"执行链的一层"，否则层数是否冻结仍有歧义。
3. **SessionManager 与 Session 的关系**：第三节说 Session 是上下文（横切），第五节又设 SessionManager 负责 Session。Session 的生命周期由谁驱动、与 ExecutionContext 如何衔接，需明确。
4. **生命周期统一后的能力损失**：第七节统一为 Initialize/Execute/Cancel/Dispose，但文档 07 的 Task 有 Pause/Resume/Progress，文档 06 的 Driver 有 Health/GetVersion/GetCapability。这些方法是合并进统一接口、还是作为可选扩展，需明确。
5. **Checkpoint 机制是否保留**：00-A 的 Command → Diff → Checkpoint（每 100 条完整快照）在基线中只提"Undo 回滚 Command"，未说明 Checkpoint 是否仍是实现手段。需明确撤销的底层实现。
6. **Capability 校验时机**：Capability 退出执行链后，`HasCapability(OCR)` 的判定发生在哪一层（Command 生成时？TaskManager 调度前？）未定义，需明确以免出现无能力却下发 Task 的情况。
7. **Pipeline / Execution Graph 的定位**：第 08 章要写 Pipeline 与 Execution Graph，但基线禁止新增核心层。需明确它们是 TaskManager 的内部编排机制（DAG 调度），而不是新的第九层。
8. **Service 退出后 HistoryService 的存废**：00-A 明确"取消 HistoryService"，但基线第二节又把 HistoryService 列为横切业务示例。两处冲突，需明确 History 的最终归属。
9. **Action 是否算独立层**：冻结链路把 Action 列为一层，但文档 07 定义 Action 是"用户交互来源（按钮/菜单/AI/插件）"。它究竟是独立层还是 Command 的输入来源，需明确。
10. **未解的老问题仍在**：Office 转换引擎选型；OCR 引擎 Windows 落地（Paddle/Tesseract）；能力矩阵图片 Convert 格；Cloud Provider 与"无联网"冲突；按需下载与"可离线"冲突；轻量化与运行时体积。这些不属于架构层，但仍是 MVP 关键路径的未定项。
