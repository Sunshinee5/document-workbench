## 一、总体判断

**不能作为正式规范直接采信，必须修文档后才能宣布"架构冻结完成"。**

文档 11 在概念层面没有违反冻结令（未新增 Manager、未新增 Context、未新增层，History 归 Session、CheckpointStore 命名正确），这一点做得比前几章干净。但它有一个系统性缺陷：**全章描述的是"应该有"的机制，而骨架里既没有对应的类型，也没有对应的调用通道**——Command 拿不到 TaskManager、undo 拿不到 Context、History 连结构体都不存在、Document 在整个冻结链路里没有任何写入口。这类落差在 08/09/10 章属于"留待 Stage 2 填充"，但 Command 是真值源，它的数据结构和签名一旦定错，Stage 3 的编辑能力要整体返工。此外第十八节的 `history.json` 与 10 章刚裁定完的 session/workspace 双 json 分工再次冲突，属于重蹈上一轮 blocking。

## 二、Blocking 清单

### 【B-01】P0｜Command → Task 的创建通道完全缺失，且 TaskManager 无归属

**问题**：第三节规定"Command 创建 Task"，08 章第一节/第八节也要求"Command → 创建 Task Graph"。但骨架 `command.rs:12` 的 `Command::execute(&self, context: &ExecutionContext)` 只有 `&self` 和 Context，既拿不到 `TaskManager`，也没有任何返回 Task 的出口。真实代码里 Task 是 **IPC 层创建的**：`apps/dw-desktop/src/ipc.rs:88-91` 直接 `TaskManager::new()` + `submit(Box::new(RotateTask::default()))`，与 Command 毫无关系。同时 `TaskManager::submit` 接收的是**已构造好的** `Box<dyn Task>`（`task.rs:103`），按定义"创建 Task 的人"是调用方，也就是现在的 IPC。
更严重的是归属问题：`ipc::new_session` 每次请求都 `TaskManager::new()`，说明 TaskManager 至今**没有长生命周期持有者**。Command 即便想持有引用也无处可取；若为此引入全局单例，等于绕过 V1.1 第二条"Manager 是横切基础设施"的定位而不作声明。

**影响**：冻结执行链的第一环 `Command → TaskManager` 在代码中不存在。Stage 2 一旦落地 OpenDocumentCommand，必然继续由 IPC 拼装 Task，冻结规则被就地作废。

**建议修正**：不得让 Command 持有 `TaskManager`（Command 变成调度者，违反"Command 只表达意图、TaskManager 只调度"）。改为 **Command 产出 Task、TaskManager 执行**：

```rust
fn build_tasks(&self) -> Result<Vec<Box<dyn Task>>, DwError>;   // Command 侧：创建 Task
pub fn submit_all(&mut self, tasks: Vec<Box<dyn Task>>, ctx: &ExecutionContext<'_>) -> Result<(), DwError>; // TaskManager 侧
```

`build_tasks` 不接触 Driver、不接触 Runtime，Capability Gate 仍由 TaskManager 在入队前统一执行（V1.1 第九条不变）。同时文档必须补一节说明 **TaskManager 的持有者是谁**（建议：`dw-desktop` 的 Tauri `State<CoreState>` 持有 SessionManager + TaskManager，ViewModel 经 IPC 取用），这是 11 章不可回避的落地前提。

### 【B-02】P0｜`CommandExecutor` / `CommandRegistry` 是未定义的第四 Manager（改名规避）

**问题**：第二十节目录首次出现 `CommandExecutor`，第二十节 + 第四/十八节隐含 `CommandRegistry`。上位文档从未定义这两个组件；按职责（持有 TaskManager、驱动 History、发事件），`CommandExecutor` 实质就是"Command 的管理者"——即第四个 Manager，只是换了个名字。这正是 00-B 第一节点名禁止的"ExecutionManager / WorkflowManager"同类物。

**影响**：Stage 1 收口报告"无第八层"的结论将被推翻；下一次评审无法再用"三个 Manager"作判据。

**建议修正**：二选一并写入文档——(a) 取消 `CommandExecutor`，Command 的驱动由 ViewModel 直接完成（`build_tasks` → `submit_all` → `history.push`），`CommandRegistry` 降级为 `command.rs` 内的 `HashMap<CommandKind, CommandFactory>` 静态表，不算组件；(b) 保留但明确声明其为**无状态纯函数**，不持有任何 Manager：

```rust
pub fn execute_command(cmd: &mut dyn Command, ctx: &ExecutionContext<'_>,
                       tasks: &mut TaskManager, history: &mut History) -> Result<(), DwError>;
```

推荐 (a)，符合"能不新增就不新增"。

### 【B-03】P0｜`undo`/`redo` 缺 Context，且全链路没有任何 Document 写路径

**问题**：`command.rs:12-14` 是 `fn undo(&mut self) -> Result<(), DwError>`，无 Context。而 Document 只能从 `ExecutionContext` 取得，因此第十四节的"Undo → History 读 Command → 执行 Undo 策略 → Document 恢复"无法实现。
但只补 Context 参数**仍然不够**：`context.rs:34` 是 `document: &'a Document`（不可变借用），`IExecutable::execute(&self, ...)` 也是 `&self`，`Document` 无任何内部可变性。**整个冻结链路（Command / Task / Driver）目前没有一条能修改文档的路径**。这是 8 字段冻结 + 全 `&self` 签名共同造成的表达力空洞，不是笔误。

**影响**：Stage 3 所有编辑能力（旋转、删除页、合并）无法落地；Undo 更无从谈起。这是本文档最深的结构性问题。

**建议修正**：(1) `undo`/`redo` 补 `context: &ExecutionContext<'_>`；(2) 文档必须显式规定 Document 的可变策略——推荐**内部可变性**，不改 Context 字段数、不新增层：

```rust
pub struct Document { pub kind: DocumentKind, state: Cell<DocumentState>, inner: RefCell<DocumentInner> }
impl Document { pub fn mutate<R>(&self, f: impl FnOnce(&mut DocumentInner) -> R) -> R; }
```

并明确"文档修改只允许发生在 Task/Driver 经 `Document::mutate` 的调用内，Command 只记录意图与 Undo 语义"。

### 【B-04】P0｜History 在代码中不存在，真值源没有载体

**问题**：第七节要求 History 保存 Command Metadata / Undo Cursor / Checkpoint Reference 三项，第六节称"History 记录 Command"为真值源。骨架 `session.rs:36` 只有 `history_index: usize` 一个裸字段，没有 History 结构体，`CheckpointStore{}`、`Recovery{}` 均为空结构体，无任何方法。

**影响**：真值源是"文档 11 的全部价值所在"，却连字段都没有定义。第十八节的 `history.json` 也就没有序列化源。

**建议修正**：在 `session.rs` 定义 History（属 Session，不新建 Service/Manager）：

```rust
pub struct History { entries: Vec<CommandMeta>, cursor: usize, checkpoint: Option<CheckpointRef>, capacity: usize }
impl History {
    pub fn push(&mut self, meta: CommandMeta);          // 截断 cursor 之后的 redo 分支
    pub fn undo_target(&self) -> Option<&CommandMeta>;
    pub fn redo_target(&self) -> Option<&CommandMeta>;
}
```

`Session.history_index: usize` 改为 `history: History`（会波及 `lib.rs` 骨架测试的构造语句，需同步）。文档需补：cursor 语义（指向"下一条待执行"还是"最后已执行"）、容量上限、cursor 之后被新 Command 截断的规则（第八节完全没提 redo 失效）。

### 【B-05】P0｜`history.json` 与 session.json / workspace.json 真值源再次冲突

**问题**：10 章修正版第十节已裁定 `session.json = {sessions, recoveryInfo, checkpointReference}`、`workspace.json = {tabs, layout, viewState, theme}`，并写明"两者禁止重复保存同一字段"。11 章第十八节又引入 `history.json`，且**不给路径、不说明与 session.json 的 `checkpointReference` 关系**。而 V1.1 第六条明确"History 属于 Session"，History 理应落在 session 目录内，不是第三个全局文件。另外第十八节"第一阶段只保存 Command metadata，不保存完整对象"直接导致：崩溃恢复后只有 metadata，没有 Command 实例，**undo 栈不可重建**——文档对此完全沉默。

**影响**：与上一轮 `10-Workspace` 的 blocking-3 完全同构，若放行则"双真值源"变成"三真值源"，恢复时以谁为准无法判定。

**建议修正**：定为每 Session 一份、位于 Session 恢复目录内，不构成第三个全局真值源：

```
Recovery/session-001/session.json     # 会话状态 + checkpointReference + historyCursor（不含 commands 列表）
Recovery/session-001/history.json     # commands 元数据 + cursor
Recovery/session-001/checkpoint/      # 二进制快照
```

并明确：metadata 经 `CommandRegistry` 重建为 Command 实例（可行则 undo 跨重启可用），若重建失败则降级为"只读历史，undo 栈清空"——必须二选一写清楚，否则 Stage 3 会做出两套行为。

### 【B-06】P1｜跨文档操作与"单 Session 单 Document"矛盾，且骨架本身已自相矛盾

**问题**：09 章第五条定"Session A → PDF A、Session B → PDF B"，即一 Session 一 Document。第十六节的"合并 A.pdf + B.pdf → C.pdf"在冻结的 8 字段 Context（`document: &'a Document` 单个引用）下无法表达。**更麻烦的是骨架自己就不一致**：`workspace.rs:9` 是 `documents: Vec<Document>`（多文档，且按值持有），而 `context.rs:34` 只暴露单文档引用，且 `Workspace` 没有任何 `document()` 访问器——Context 里的 `document` 当前**无处可取**（`ipc.rs:65` 只能临时 new 一个局部 Document）。

**影响**：ExecutionContext 的 document 字段目前是"悬空引用"，Stage 2 打开 PDF 时必然卡住。

**建议修正**：明确"一 Session 一 Document"为准，`Workspace.documents` 降为 `Option<Document>` 或改为 `current: Document`（Tab 级多文档属 10 章范畴，须在 10 章另裁）；跨文档 Command（合并/比较）定义为**以文件路径为输入、以新文档为输出**，不依赖多个 Document 引用，且只允许在"目标 Session 尚无 Document"时执行。同时补 `Workspace::current_document(&self) -> Option<&Document>` 供 TaskManager 构造 Context。

### 【B-07】P1｜Checkpoint 与 Diff 语义丢失，与 V1.1 第四条冲突

**问题**：V1.1 第四条冻结的是两层：`Command → Diff → Checkpoint`，恢复为 `Checkpoint + 后续 Diff → 当前状态`。11 章第十节把链路改写成"Command → 产生变化，Checkpoint → 保存当前状态"，**Diff 整层消失**；第十一节改为"每 100 条 Command 生成一个完整快照"，第十二节"保存压缩状态"。文档未定义 Checkpoint 的内容格式（原始文件副本？序列化 Document？增量？），也未定义 Diff 存哪。

**影响**：撤销的存储层实现方式悬空，Stage 3 会在"整文件快照"与"增量 diff"之间反复。

**建议修正**：补一节定义 Checkpoint 载荷（推荐第一阶段：源文件字节 + Command 游标的整包快照，Diff 推迟到 Stage 4 并书面声明），并显式说明与 V1.1 第四条的关系（是"分阶段落地"还是"修订 Diff 层"）。

### 【B-08】P1｜Undo 混合模式的判定条件完全缺失，且方式 2 描述有误

**问题**：第九节称"最终采用混合模式"，但全文没有说谁判定、按什么标准判定某条 Command 走反向操作还是 Checkpoint 恢复。且方式 2 写成"Checkpoint → 重新执行 Command"——语义错误：撤销的流程是"恢复到更早的 Checkpoint，再**重放其后**未被撤销的 Command"，而不是重新执行被撤销的那条。

**影响**：Stage 3 实现时必然停摆；若照字面实现会得到"undo 后状态更前进"的错误行为。

**建议修正**：把判定条件收敛为**每条 Command 自己声明**，不设全局策略（避免引入 Strategy，00-B 第四条已取消）：

```rust
fn undo_mode(&self) -> UndoMode { UndoMode::Inverse }   // 默认反向操作
```

`UndoMode::Checkpoint` 时由 History 找到最近的 `CheckpointRef` 并重放游标之后的 Command。同时修正方式 2 的表述。

### 【B-09】P1｜Command 数据结构的 Rust 落地无解，且 dw-core 零依赖

**问题**：第四节 6 字段（id/type/timestamp/parameters/target/status）是 C#/JSON 思维：Rust trait object 无运行时反射，`type` 字符串到具体类型无映射路径，`parameters` 异构无法表达，序列化 trait object 需 `typetag` 类方案。第二十节又要求 `CommandRegistry` 却不给注册键。**且 `dw-core/Cargo.toml` 明确"核心库保持零外部依赖"**，第十八节的 json 持久化必然要引入 serde，文档对此零声明。

**影响**：Stage 3 第一天就要做技术选型，可能引入 `uuid`、`chrono`、`typetag` 三个非计划依赖。

**建议修正**：放弃"统一 Command struct + 异构 parameters"，改为"**具体 Command 结构体 + 元数据视图**"：`id: u64`（Session 内单调递增，不引 uuid）、`timestamp: u64`（Unix 毫秒，不引 chrono）、`CommandKind` 枚举替代 `type` 字符串、`fn metadata(&self) -> CommandMeta` 输出可序列化元数据；`CommandRegistry` 用 `CommandKind → fn(&CommandMeta) -> Result<Box<dyn Command>, DwError>` 函数工厂，**不序列化 trait object**。并在 11 章明确"`dw-core` 是否允许引入 serde"（建议允许，仅 `serde` + `serde_json`，写进 00-D 或本章附注）。

### 【B-10】P1｜Command 五态生命周期重叠，失败态无表达

**问题**：第五节 `Created → Executed → Committed → Recorded → Undo Available` 中，Committed 与 Recorded 的区别文档未定义（读起来都指"已完成并入库"），"失败不进入 History"只给结论不给状态，Undo Available 更像派生属性而非状态。

**建议修正**：收敛为三态 `Created → Executed → Recorded`；失败用 `Result` 表达（`DwError` 已足够），不占状态位；"可撤销"由 `History.cursor > 0 && entry.is_undoable()` 派生，不设为状态。另需补：Document 的脏标记（`DocumentState::Modified`）由谁置位、Command 失败时是否回滚 Document。

### 【B-11】P1｜目录命名不一致

**问题**：第十二节 `Recovery/SessionID/checkpoint/`，09 章第十六节 `Recovery/session-XXX/session.json`，骨架 `dw-runtime` 已使用 `Recovery/temp`。

**建议修正**：统一为小写 `Recovery/session-001/{session.json, history.json, checkpoint/}`，并说明 `SessionID` 的生成规则（`session-{三位序号}`，与 09 章一致）。

### 【B-12】P1｜`ExportWordCommand` 例子误导，且与 08 章不一致

**问题**：第十五节用它做"多 Task Command"的示例（Prepare/Convert/Save），但导出**不修改 Document**，"Undo 只撤销最终状态"实际是"删除外部导出文件"——这不该进 History，也不该有 Undo 语义。同时 08 章第一节的同一例子是 **4 个 Task**（Prepare/Convert/**Layout**/Save），11 章写成 3 个，两处不一致。

**建议修正**：改用真正修改文档的例子（`DeletePagesCommand` → `RewritePagesTask` + `RebuildIndexTask`；`MergePdfCommand` 见第十六节）。导出类 Command 明确标注 `is_undoable() == false`，不进 History——这恰好给第五节"失败不进入 History"提供了对称机制。并回写 08 章统一 Task 数量。

### 【B-13】P1｜EventBus 三事件归属不明，发布者缺失

**问题**：第十九节要求发 `CommandExecuted` / `DocumentChanged` / `HistoryChanged`，但骨架 `eventbus.rs:22` 只有 `Event::task_completed`，`Event{kind: String, message: String}`。更关键的是**没有说明由谁发**：Command 拿不到 EventBus（同 B-01 的根因），TaskManager 只发 Task 级事件（08 章第十五节），而 `DocumentChanged` 已被 10 章第十三节分配给 Workspace 监听。

**影响**：三个事件可能永远无人 publish；`Event.kind` 用 String 也让 UI 只能做字符串比较。

**建议修正**：`CommandExecuted` 与 `HistoryChanged` 在 execute 时总是成对发生，合并为一条带载荷的事件，`EventKind` 改枚举（不是新层，属既有组件的实现细化）：

```rust
pub enum EventKind { TaskStarted, TaskProgress, TaskCompleted, TaskFailed,
                     CommandRecorded { kind: CommandKind, cursor: usize, can_undo: bool, can_redo: bool },
                     DocumentChanged }
```

`CommandRecorded` 由执行 Command 的调用方（ViewModel）在 `history.push` 之后发布；`DocumentChanged` 保留（undo/redo 后也必须发，否则 Workspace 的 ViewState 不刷新——这一点文档完全没写）。`HistoryChanged` 删除。

### 【B-14】P1｜"Session 恢复"验收项与 09 章职责重复

**问题**：第二十二节验收列"Session 恢复"，但 09 章第十六节已完整定义 Session 恢复（当前文档、当前页、Workspace、Checkpoint，不恢复运行中 Task）。

**建议修正**：11 章的验收项改为"**History 恢复**（cursor 与可撤销性重建）"，并声明"Session / Workspace 恢复由 09、10 章负责，本章只负责 history.json 的读取与 cursor 还原"。

### 【B-15】P2｜目录结构为 C# 风格，与现有 Rust 平铺布局冲突

**问题**：第二十节 `Core/Command/`、`Core/Session/` 与骨架 `dw-core/src/*.rs` 平铺单文件不符；09、10 章同样风格。

**建议修正**：明确"不新增 crate（workspace members 已冻结 6 个）"，给出拆分阈值：单文件超约 400 行或出现 3 个以上独立职责时，`command.rs` → `command/{mod.rs, registry.rs, history.rs}`；否则保持平铺。文档统一用 Rust 模块路径（`dw_core::command`）而非目录树表述。

### 【B-16】P2｜"批处理"作为第五种来源与冻结枚举冲突

**问题**：第一节列"批处理"为 Command 来源，但 `action.rs:6` 的 `ActionSource` 与 `command.rs:21` 的 `CommandSource` 均只有 User/AI/Plugin/Macro 四变体（冻结定义）。批处理在 `CHANGELOG.md`、`Stage1-收口报告` 中明确属 Stage 5。

**建议修正**：**不建议补 `Batch` 变体**（会变成第五种来源，属新增概念）。改为：批处理是"一次触发 N 条 Command"的**入口**，每条 Command 仍带原有四类 source。第一节措辞改为"批处理入口 → N 条 Command"。

## 三、设计缺口清单（不阻断 Stage 2，但 Stage 3 前必须补）

1. **History 容量与淘汰**：无上限则内存与 history.json 无界增长；需定义 `capacity` 与淘汰时 Checkpoint 的失效规则。
2. **redo 分支截断**：cursor 之后有新 Command 时 redo 栈作废，文档未写（B-04 已并入）。
3. **Checkpoint 触发时机与失败回退**：第 100 条 Command 执行前还是后生成？生成失败是否阻断？磁盘空间不足如何处理？
4. **Checkpoint 载荷格式**：见 B-07，需定义二进制格式与版本号（否则 Stage 4 改格式无法兼容旧 Recovery 目录）。
5. **多 Session 并发写 Recovery**：两个 Session 同时退出时的写盘顺序与部分写入（原子写：临时文件 + rename）。
6. **Command 幂等与重放**：Checkpoint 恢复后重放 Command 时，非确定性 Command（依赖当前时间/随机/外部文件）如何处理。
7. **非撤销 Command 的边界**：导出、打印、OCR（产生新文档）是否进 History，需一张明确清单。
8. **Command 与 Document 状态机联动**：`DocumentState::Modified` 的置位/清除时机、保存后 History 是否清空（"保存点"概念）。
9. **AI 生成多 Command 的事务性**：AI 一次生成 N 条 Command（00-B 第十一条），是逐条进 History 还是作为一个 undo 单元——文档未定义，Stage 5 会返工。

## 六、结论

**不可宣布"架构冻结完成"，必须先修文档 11。**

- 五个 P0（B-01～B-05）中，B-01/B-03/B-04 是签名与结构级缺陷，直接决定 Stage 2 骨架形态，**必须在写第一行 PDF 代码前修完**；B-05 是上一轮已裁定过的同类问题，不能二次放行；B-02 若不澄清，Stage 1 收口报告"无第八层"的结论失效。
- B-06～B-16 属需澄清，可与 Stage 2 并行，但 **B-07、B-08、B-09 必须在 Stage 3 开工前关闭**，否则编辑能力无法实现。
- 建议流程：修 11 章（P0 五项 + B-06/B-09 一并改）→ 同步改 `command.rs` / `session.rs` / `document.rs` / `workspace.rs` / `ipc.rs` → 跑 GNU target 回归 → 出《核对记录-11 修正版》→ 再宣布冻结完成并进 Stage 2。
- 若用户希望 Stage 2 立即并行开工，可接受的**最低条件**是：先落地 B-01（`build_tasks` + `submit_all`）与 B-03（`undo` 补 Context + Document 内部可变性）两个签名，因为"打开 PDF"同样要走 Command → Task 这一环，签名晚改等于 Stage 2 全量返工。
