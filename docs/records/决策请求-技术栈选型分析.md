## 一、项目是什么

Document Workbench 是一个面向 Windows 的**本地绿色版文档工作台**，不是 PDF 工具箱。第一阶段（MVP）只做 PDF 阅读与常用编辑、Office⇄PDF 转换、OCR。

产品目标原文：**"比 PDFgear 更开放、比福昕更轻、比 WPS 更干净"**。

硬约束（验收标准，不可妥协）：

- Windows 绿色版，双击即可运行。
- 全部简体中文，无广告，无登录。
- 不依赖云端，可离线。
- 可二次开发，Agent 可持续维护。
- 为第二阶段插件化、AI、工作区预留扩展点。
- 第一阶段明确不做：AI 总结/翻译、插件市场、企业版、云同步、多人协作、账号系统、登录、收费、在线 PDF。

第一阶段验收：打开 PDF 速度接近 SumatraPDF；能完成 Word⇄PDF 转换；能完成页面管理（合并/拆分/旋转/排序）；能 OCR 生成可搜索 PDF。

## 二、架构已冻结（技术栈选型不能破坏的部分）

经过 9 章、连续多次推翻后，架构已于补充决议 V1.1 冻结。**以下与技术栈无关，任何技术栈都必须遵守**：

**唯一执行链（禁止新增层）**：

```
UI → ViewModel → Action → Command → Task → Driver → Runtime
```

**横切组件（不进入执行链）**：Session（共享状态）、ExecutionContext（统一上下文）、Capability（静态能力声明 HasXXX）、Service（横切业务组织）、三个 Manager（DriverManager / TaskManager / SessionManager）。

**关键机制**：

- Capability Gate：Task 入队前在 ExecutionContext 上做 `HasCapability()` 校验，全链路只检查一次。
- Undo 两层：语义层 Command（唯一真值源）+ 存储层 Checkpoint（优化恢复，每 100 条 Command 生成，优先落盘）。
- 生命周期：`IExecutable`（Initialize/Execute/Cancel/Dispose）+ 扩展 `IPausable`（Task）、`IHealthCheck`（Driver）。
- AI 唯一身份 = Command Generator，禁止直接调 Runtime。
- Driver 屏蔽所有第三方名字（系统里不出现 Paddle/PDFium/LibreOffice），Driver 只做四件事：调第三方、转数据、统一错误、能力检测。
- Runtime 只放 DLL/EXE/SDK/Model/CLI/动态库/本地服务，禁止业务。
- 禁止"概念驱动开发"：新想法必须过三问（现有架构真解决不了？是新能力还是已有实现？是否减少复杂度？）。

**实现设计顺序**：08 Execution Graph → 09 Session（已写）→ 10 Workspace → 11 Command/Undo/Checkpoint → 12 Driver 加载。

## 三、冲突陈述

工程骨架开工指令中出现：

> CMake、Qt、MVVM、`RotateTask::Execute(){}`（C++ 语法）

而开发文档 01 与架构决议 00-A 已冻结：

> Tauri 2.x + React + TypeScript + Vite；Rust 生态；lopdf 做 PDF 底层对象操作；明确禁用 Java 运行时（PDFBox）。

两套技术栈不可兼得。若改 Qt/C++，以下已定决策连锁失效：

| 已定项 | Qt/C++ 方案下的影响 |
|--------|---------------------|
| Tauri 2.x + React + TS + Vite | 全部作废，前端换成 Qt Widgets 或 QML |
| lopdf（Rust PDF 对象库） | 作废，需换 C++ PDF 库 |
| PDFium 集成方式 | 从 Rust 绑定改为 C++ 原生 API 直接调用 |
| 00-A 取消 PDFBox 的理由 | 理由为"Rust 生态塞 JRE 很奇怪"，改用 C++ 后该理由不再成立（但 PDFBox 是 Java，是否重新考虑需决断） |
| 未来 AI / 插件 / Web 能力 | Tauri/React 路线前端生态优势消失，Qt 下需另找方案 |
| 绿色版体积模型 | Qt 静态/动态链接的体积与 Tauri+WebView2 的体积模型不同，需重新测算 |

若维持 Tauri/Rust，则骨架清单里的 CMake、Qt、C++ 示例全部作废，改为 Cargo + npm + Rust/TS。

## 四、候选方案详述

### 方案 A：Qt 6 + C++ + CMake

- **界面**：Qt Widgets（或 QML），C++ 编写，CMake 构建。
- **内核**：C++ 实现 Capability / Task / Driver / Session / Command。
- **PDF**：PDFium C++ API（渲染）+ 需选定 C++ PDF 对象库（lopdf 的替代，如 PoDoFo / qpdf / PDFium 自身对象模型）。
- **Office 转换**：LibreOffice headless（进程调用）。
- **OCR**：Windows OCR（默认）+ Tesseract（可选）+ PaddleOCR（插件）。
- **优势**：原生桌面性能强、启动快；Qt 信号槽天然适合事件总线；PDFium 是 C++ 库可零成本直接调；Qt 有成熟的 Dock 停靠窗口组件（Workspace 章节需要）；单exe绿色版打包路径成熟（windeployqt + 静态链接）。
- **劣势**：推翻已冻结的 01/00-A 技术栈；C++ 开发效率与内存安全成本高于 Rust/TS；前端生态（AI、Web 组件）弱于 React；需重新选型 C++ PDF 对象库；Agent（AI）写 C++ 的可靠性通常低于写 TS/Rust。

### 方案 B：Tauri 2.x + React + TypeScript + Vite + Rust

- **界面**：React + TS + Vite，Tauri 2 壳。
- **内核**：Rust 实现 Capability / Task / Driver / Session / Command；前端实现 UI / ViewModel。
- **PDF**：PDF.js（阅读 Viewer）+ PDFium Rust 绑定（渲染）+ lopdf（对象操作）。
- **Office 转换**：LibreOffice headless（进程调用）。
- **OCR**：Windows OCR（默认）+ Tesseract（可选）+ PaddleOCR（插件）。
- **优势**：与已冻结文档完全一致，无需返工；体积小、内存低、启动快，最贴合"比福昕更轻"；React 生态利于未来 Workspace / 插件 / AI；Rust 内存安全、适合 Agent 生成代码；lopdf/PDFium 绑定已有现成方案。
- **劣势**：Tauri 依赖 Windows WebView2（旧系统需引导安装，与"可离线双击运行"有张力）；PDF.js 与 PDFium 双引擎边界需明确（Capability 架构下可解耦）；Rust + TS 双语言桥接（IPC）增加复杂度；Qt 式 Dock 停靠窗口需用 React 组件自行实现。

### 方案 C：Qt 界面 + Rust 内核（FFI 混合）

- **界面**：Qt 6（C++/QML）。
- **内核**：Rust 实现 Task / Driver / Capability / Session / Command，通过 FFI 暴露给 Qt。
- **PDF**：沿用 PDFium + lopdf（Rust 侧）。
- **优势**：兼顾原生界面（Dock、性能）与已选 Rust 内核（安全、lopdf 复用）。
- **劣势**：复杂度最高——两套语言、两套构建系统（CMake + Cargo）、FFI 边界调试成本、跨语言生命周期管理（Session/Driver 在 Rust、UI 在 C++）、Agent 维护难度最大。除非有强理由，一般不推荐混合架构。

## 五、决策维度对比

| 决策维度 | A: Qt/C++ | B: Tauri/Rust | C: Qt+Rust |
|----------|-----------|---------------|------------|
| 与现有冻结文档一致 | ✗ 需改 01/00-A | ✓ 完全一致 | ✗ 需改前端部分 |
| 绿色版体积 | 中（Qt 链接） | 小（但含 WebView2） | 大（双运行时） |
| 启动速度 | 快 | 快 | 中 |
| 离线双击运行 | ✓ | ⚠ WebView2 依赖 | ✓ |
| PDFium 集成 | ✓ 原生直接调 | ⚠ 需 Rust 绑定 | ✓ Rust 绑定 |
| PDF 对象库 | 需重新选型 | lopdf 已定 | lopdf 已定 |
| 原生 Dock/停靠窗口 | ✓ 现成 | ⚠ 自研 React 组件 | ✓ 现成 |

| 构建复杂度 | 中（CMake） | 中（Cargo+npm） | 高（双系统 FFI） |
| 二次开发友好度 | 中 | 高 | 低 |

## 六、需要决断方回答的核心问题

1. **产品优先级**："比福昕更轻"与"原生桌面体验"哪个更重要？这直接决定 A 还是 B。
2. **WebView2 是否可接受**：Tauri 依赖 WebView2，Windows 10/11 通常预装，但若目标包含旧系统，绿色版离线双击会受影响。是否能接受首次运行引导安装 WebView2？
3. **是否接受推翻已冻结文档**：选 A/C 意味着文档 01、00-A 的技术栈部分作废，需要重写并重新同步所有派生文档。这个成本是否可接受？
4. **AI/Agent 维护权重**：项目明确要求"Agent 可持续维护"。C++/Qt 与 Rust/TS 对 AI 生成代码的可靠性差异是否纳入决策？
5. **未来前端扩展**：第二阶段插件化、AI 功能、可能的 Web 组件——React 生态是否是刚需？
6. **C++ PDF 对象库选型**：若选 A，是否已有偏好的 C++ PDF 库（PoDoFo / qpdf / PDFium 对象模型）？这会影响 MVP 页面管理能力的实现成本。
7. **混合架构的必要性**：选 C 的前提是什么？是否有 Qt 界面不可替代的具体需求（如特定 Dock 行为）？

## 七、整理者的中立观察（不替决断）

- 若**不改变现有文档**是首要目标 → B 是唯一不返工的选择。
- 若**原生桌面体验与 PDFium 直接调用**是首要目标 → A 更短平快，但要承担重写文档与 C++ 维护成本。
- C 只在"Qt 界面有不可替代需求且 Rust 内核必须保留"时成立，否则是复杂度自找。
- 无论选哪套，架构冻结（执行链、Manager 数量、Context 数量、生命周期、Capability Gate、Undo 两层）都不受技术栈影响，可以原样落地。这一点可以放心。
- 一个容易被忽略的点：**CMake 和 Qt 出现在骨架指令里，但架构文档从未讨论过技术栈变更**。建议决断方先确认这是有意变更，还是举例时的随口表述——这决定了要不要真的推翻已冻结文档。
