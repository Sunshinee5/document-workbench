## 4. C 功能正确性

**C1 History undo/redo 语义 —— ✓ 正确。** session.rs:160-176。A/B/C 三条 cursor=3；`undo()` 先 `cursor-=1` 再取 `entries[cursor]` → 返回 C、cursor=2；`redo()` 取 `entries[cursor]` 再 `cursor+=1` → 返回 C、cursor=3。空 history undo 命中 `cursor==0` 返回 None 不 panic；cursor 在末尾 redo 命中 `cursor>=len` 返回 None。redo 分支截断（session.rs:146-148）在 `cursor<len` 时 `truncate(cursor)` 再 push，A/B/C→undo→record(D) 得 [A,B,D] 正确，有测试 `history_redo_truncates_branch` 实证通过。

**C2 容量淘汰 —— 算术正确，但潜在缺陷「成立且比假设更严重」。** session.rs:152-156：`overflow=len-capacity; drain(0..overflow); cursor=cursor.saturating_sub(overflow)`，因 record 时 cursor==len 恒成立，淘汰后 cursor==capacity==len，无误。**但 Lead 的假设「checkpoints 指向被丢弃的命令」不成立**：`CheckpointRef`(diff.rs:15) 是快照文件路径 `String`，非 entries 下标，且 `push_checkpoint`(session.rs:199) **零调用点**，Stage 1 checkpoints 恒空。真正缺陷是：淘汰 `drain` 丢掉 CommandRecord 及其 `diff_reference`，却**从不删除磁盘上的 diff 文件** → diff 文件孤儿化（磁盘泄漏）+ 被淘汰窗口永久不可撤销（即便文件还在）。这才是 Stage 3 会踩的坑。

**C3 DocumentStore id 分配 —— ✓ 不复用。** session.rs:54-64 `next_id+=1` 从 1 起；`remove`(72-74) 只 `HashMap::remove`，**不重置 next_id**，故 remove 后再 create 得到新递增值，id 不复用。

**C4 RwLock 锁中毒处理 —— 可接受但需注意。** document.rs:107-124 用 `unwrap_or_else(|p| p.into_inner())` 静默恢复。中毒意味着持写锁线程 panic，`DocumentInner` 可能半更新不一致；静默继续等于「在可能损坏的状态上继续编辑」。Stage 1（仅 `revision:u64`）无害；Stage 2 引入页序/页属性后，建议改为上报错误或至少记日志，而非无条件恢复。

**C5 SessionManager 借用分段与锁序 —— ✓ 正确、无死锁。** ipc.rs：段1 可变 136-147、段2 不可变 151-189、段3 可变 192-211，各自独立作用域。段2 内 `session` 同时供 `ExecutionContext.session` 与 `&session.workspace`/`&session.selection` 借用，全为不可变，无冲突。锁获取顺序恒为 session→task→driver→event（段2 内嵌套获取），段1/段3 仅取 session，末尾仅取 event，全仓无反向顺序 → 无环，不死锁。

**C6 session_count 贯通 —— ✓ 一致。** 后端 `SessionInfo.session_count`(ipc.rs:100) ← `session_count()`=map.len()(session.rs:338)；前端 `SessionInfo.session_count`(ui/src/ipc/index.ts:29) → `WorkbenchState.sessionCount`(viewmodels:17) → `createSession()` 写入(viewmodels:81)。点两次新建：每次 `create_session` 插入新 id 并置 active，count=1→2，UI 显示「会话 2 个」，符合预期。

## 5. D 发现的问题（按严重度）

**D-1【需修·Stage 2】Session 无限累积（内存泄漏成立）。**
【证据】ipc.rs:138 每次 new_session 都 `create_session()`；session.rs:306 `sessions.insert`；`close_session`(329) 全仓**零调用点**。旧 Session（含 DocumentStore/History）永不释放。
【建议】Stage 2 改「单活动会话 + 新建时关闭旧会话」，或显式暴露关闭 UI 调用 `close_session`。

**D-2【需修·Stage 2】History 无法重放：params 只有中文描述。**
【证据】ipc.rs:202 `params: json!({"description":...})`；Command trait(command.rs:43-65)**无 `params()` 访问器**，History 拿不到真实参数（如 page:5）。
【建议】Command 增 `fn params(&self)->serde_json::Value`，record 时存真实参数；对照 11.1 第四节「保存 Command 类型、参数」。

**D-3【需修·Stage 2，非 Stage 1 缺陷】Diff 链路仅存类型、未接通。**
【证据】`StructureDiff/BinaryDiff/Diff` 仅在 diff.rs 定义，全仓**无任何构造点**；`diff_reference` 生产恒 `None`(ipc.rs:203)；`push_checkpoint` 零调用。文档 11.1 第九节 `Document.mutate→Diff→History` 在代码中未落地。
【判定】Stage 1 是空流程、无真实编辑，不产 Diff **属合理范围**；但必须明确「链路未通」，禁止误认为已实现——否则 Stage 2 的 Undo 会直接失效。同时 `.mutate(` 仅测试调用，生产无 Task 写文档，「可写入」目前只在单元级被证明，未经 IPC 全链路验证。

**D-4【需修·Stage 2】submit_all 缺事务语义。**
【证据】task.rs:127-130 逐个 `submit`，每个在 submit(108) 内单独过 Capability Gate 并执行；第 k 个失败时前 k-1 个已执行，无回滚。NewSession 只产 1 个 Task 无碍，但 Export 四阶段（Prepare/Convert/Layout/Save）会半执行。
【建议】Stage 2 定义批量原子性：先全量 Gate 校验再执行，或失败时执行补偿。

**D-5【可延后】checkpoints 从不修剪 + 无生成逻辑。**
【证据】session.rs:199 只 push，无 drain；且零调用 → 既不生成也不淘汰。Stage 3 需按 INTERVAL=100 生成并在淘汰时同步清理过期快照引用。

**D-6【可延后】锁中毒静默恢复**（见 C4）。Stage 2 建议改为可观测失败。

**D-7【仅记录】实现层与文档字面偏差（均不构成违规）**：
① 附二第1条建议 `create_session` 返回所有权(move)，实现改为返回 `SessionId`、所有权留在 Manager(session.rs:300)——此改动**更优**，契合「SessionManager 是 Session 唯一持有者」，非违规。
② 附二第5条要求加 `thiserror`，实际未加，error.rs 手写 `Display/Error`——等价，非缺陷。
③ 测试未覆盖容量淘汰与锁中毒路径（覆盖缺口，非错误）。
