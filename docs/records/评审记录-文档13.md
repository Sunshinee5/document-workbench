### P0-2　Session 模型冲突

- **文档位置**：§13「一个 Session 一个 Document。跨文档操作必须创建新 Session。」（200–202 行）
- **冲突对象**：`00` §3（DocumentStore）、§6.2、§6.3；`01` §1.2、§1.3、§2.2
- **具体矛盾**：`00` §3 明确 Session 内含 `DocumentStore { HashMap<DocumentId, Document> }`，唯一持有多个 Document；Workspace 的 `Tab { document_id, title }` 多标签设计，正是建立在"一个 Session 多 Document"之上。文档13要求一 Session 一 Document，与其自身 §13 下半「Session 不执行业务」虽不冲突，但与多标签根本冲突。
- **影响**：照做则每次切文档都要新建 Session，而 History / Selection / Checkpoint / Clipboard 全是 Session 成员（`00` §6.2.3）——切文档即全丢，撤销历史与多标签同时报废。这是**摧毁性**改动。
- **建议改法**：删除这两句，改写为「一个 Session 持 DocumentStore，可含多 Document；Tab 仅存 document_id；多 Session 严格隔离」（对齐 `00` §3/§6.2）。保留同节「Session 不执行业务，只维护状态」。

### P0-3　PDF.js 被归进 Driver

- **文档位置**：§2「Driver：PDF：PDF.js（Viewer）、lopdf（编辑）」（60 行）
- **冲突对象**：`00` §9、§10；`03` §6；`12.1` 补充决议 §8；`05` F21
- **具体矛盾**：`00` §9 冻结 PDF.js 在 **WebView 内渲染、不产生跨 IPC 位图**；`03` §6 明确 PDF.js 位置＝前端 WebView，而 Driver 是 Rust 侧（`dw-pdf` 等 crate）对第三方的适配层。`12.1` §8「Stage 2 查看全部走 PDF.js，PDFium 退出阅读路径」。把前端 JS 库归进 Rust Driver 层是概念错位。文档13在 §2「UI」栏又列了一次「PDF Viewer（PDF.js）」，两处矛盾，作者定位不清。
- **影响**：会把 PDF.js 错误地纳入 `DriverManager::resolve` / Capability Gate 链路，引发"前端库怎么进 Rust trait"的实现混乱；并可能诱导 PDFium 回流阅读渲染（F21 禁令）。

### P1-5　History「唯一真值源」表述错误

- **文档位置**：§12「唯一真值源：`Command → Diff → Checkpoint`」（192 行）
- **冲突对象**：`00` §5 表（139–141 行）
- **具体矛盾**：`00` §5 明确 **Command = 唯一语义真值源**、Diff = 回放依据、Checkpoint = 仅加速恢复。文档13把三者并列为"唯一真值源"——不可能有三个"唯一"。（链条写法 `Command→Diff→Checkpoint` 本身与 `00` §5 一致，**错在定性**。）
- **影响**：真值源多元化会让 Undo/恢复实现出现"以谁为准"的分歧。
- **建议改法**：改为「Command 是唯一语义真值源；Diff 是回放依据；Checkpoint 仅加速恢复」。**保留**同节「Checkpoint 只负责加速恢复，不是唯一恢复来源」与「新 Command 使 Redo 失效」——这两句与冻结一致。

### P1-6　Capability Gate 流程（部分不成立）

- **文档位置**：§8「Command → build_tasks() → Capability Check → Task Queue；失败直接 TaskRejected」（150–156 行）
- **冲突对象**：`00` §4.2/§4.3/§4.5/§8.4；`02` §3.2/§3.3；`00` §0.5/§14（禁止新概念）
- **核验结论**：
  - **「Gate 在 build_tasks 之后」——不成立**。`00` §8.4「一次执行的固定顺序」写的就是 `build_tasks(ctx) → submit → capability_gate → resolve → execute_on`；`00` §4.2 要求"Gate 在 Task **入队之前**"，文档13的"Capability Check → Task Queue"满足此点。故疑点前半与冻结一致，不能判违规。
  - 附带发现：`00` §4.3/§4.5 措辞为"校验通过才创建 Task / Task 创建前调用 gate"，与 §8.4 的"build_tasks 先"存在**规范内部张力**；`02` §3.3.3 澄清"Gate 失败时 Task 已创建但未执行"，支持 §8.4。建议就此向规范维护者提 issue，不应由文档13背锅。
  - **「Task Queue」——成立**。`00` §2 明确 `ExecutionGraph` 是 TaskManager 内部 **DAG**，"不是层、不进架构图"；`00` §0.5/§14 禁止未经定义的新概念。队列语义 ≠ DAG，把内部数据结构升格为架构流程节点是错误。
- **影响**：引入与冻结冲突的调度概念，误导实现者按 FIFO 队列而非 DAG 编排。
- **建议改法**：删"Task Queue"，改为「Command → build_tasks() → TaskManager.submit → capability_gate（唯一准入点）→ resolve → execute_on」，对齐 `00` §8.4。保留"失败 TaskRejected""禁止 Driver 再查 Capability"（与 `00` §4.4/§4.6 一致）。

### P1-7　五问 vs 六问

- **文档位置**：§17「提交前必须回答五个问题：属于哪个模块／生命周期谁管／是否违反 Freeze R1／是否新增概念／是否已有组件可承担」（243–253 行）
- **冲突对象**：`00` §12；`05` §4（Q1–Q6）；`05` §6 自检清单
- **具体矛盾**：冻结的代码驱动准入门槛是**六项**——存在性四问（为什么存在/谁创建/谁销毁/谁持有）+ 实现性两问（Rust 是什么/生命周期）。`00` §12、`05` §4 口径一致。文档13的"五问"是**另一套 PR 自检清单**（模块归属/生命周期/合规/新概念/复用判断），不是概念准入标准，二者被混同，且数量口径冲突。
- **影响**：Agent 不知该答五问还是六问，可能导致新概念未过六问就进代码。
- **建议改法**：§17 删除五问，改为「新增概念按 `05` §4 六问答完并把答案写进 `00` §12 / PR 说明」；若想保留 PR 自检意图，另起一句「提交前另过 `05` §6 自检清单 + 附录 A」，不与六问并列。
