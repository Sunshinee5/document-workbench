## 一、总体判断

**不能作为正式规范采信，但方向正确，属"补齐签名"而非"重写"级别。**

文档 12 在概念纪律上是 08 章以来最干净的一章：没有新增 Manager、没有新增 Context、没有新增层，Driver 定位（能力适配、不执行业务）、Document 不持 Driver、PDFium/lopdf 职责分离、Task 不依赖具体库，六条红线全部守住了，甚至比 06 章更收敛。问题全部集中在同一个位置：**它写的是"Driver 应该是什么"，而不是"Driver 的 Rust 签名是什么"**。20 节里 6 段伪代码，无一可直接编译（`fn initialize();` 在 Rust 中非法）；最关键的三个契约——Driver 怎么被调用（参数/返回值）、谁来解析 Driver、能力双源如何合并——一个字都没有。这不是文字粗糙，而是 Stage 2 第一天就要用的三个接口没定。此外第十二节 OCR 方案与 `00-D`（最高优先级）正面冲突，第十八节禁 `PluginManager` 而 `V1.1` 交给本章的"发现 / 加载 / 隔离"三项任务全部缺失。修完 P0 六条即可采信。

## 二、Blocking 清单

### 【B-01】P0｜第四节重定义生命周期，绕开 `IExecutable` 冻结，且伪代码非法

**问题**：第四节 `trait Driver { initialize(); capabilities(); health(); dispose(); }` 丢掉了 `Execute` 与 `Cancel`。`V1.1` 第三条冻结的是"基类 `IExecutable`（Initialize/Execute/Cancel/Dispose）+ 扩展 `IHealthCheck`（Health/Version）"，真实代码 `driver.rs:15` 是 `pub trait IDriver: IExecutable + IHealthCheck + Send`。文档 12 自述"替代 06 章"，而 06 章第五节恰恰有 `Execute/Cancel`——**这是相对 06 的倒退**，不是笔误。同时四个方法均无返回类型、无 `&self`，在 Rust 中不是合法 trait 声明。
**影响**：按本文档写出的 Driver 无法注册进 `DriverRegistry`（`Box<dyn IDriver>` 需要 `IExecutable`），`TaskManager::submit` 无法调用。Stage 2 的第一个 Driver 就会撞墙。
**建议修正**：明确"基类不可改，Driver 只在基类之上**追加**执行接口"，并把第四节改为真实签名：

```rust
pub trait IDriver: IExecutable + IHealthCheck + Send + Sync {   // 追加 Sync，理由见 B-04
    fn name(&self) -> &str;                  // 稳定 ASCII id："pdfium" / "lopdf" / "null"
    fn display_name(&self) -> &str { self.name() }
    fn capabilities(&self) -> CapabilitySet;
}
```

并在文档中一句话说清 `IExecutable::execute(&self, ctx) -> Result<(), DwError>` 的定位（见 B-02），否则"基类有 Execute、具体 Driver 又有 render_page"会被读成两套执行入口。

### 【B-02】P0｜Task → Driver 的参数与返回值通道完全未定义（`DriverResult` 设计方向也错）

**问题**：这是本章最深的结构性空洞，三条互相咬合：
1. `lifecycle.rs:12` 是 `fn execute(&self, context: &ExecutionContext) -> Result<(), DwError>`——**没有输入参数、没有返回值**。而 `ExecutionContext` 8 字段冻结（`context.rs:30-47`）里只有 `Config/Progress/CancelToken`，**没有任何"任务参数"槽位**（渲染第几页、缩放多少、旋转 90 还是 180）。Task 的参数（`RotateTask{}` 这类结构体字段）在冻结链路里**无法送达 Driver**。
2. 第七节 `fn render(document, page)` / `fn rotate_page()` 只是伪代码：`document` 类型未定、返回值未定、`rotate_page()` 无参无返回无法旋转。
3. 第十节 `DriverResult { success, output, metadata, error }` 与 `Result` 语义重复（`success=false` 与 `error=Some` 是两个真值源），且与现有 `Result<(), DwError>` 无法对接。

**影响**：Stage 2 无法写出 `render_page`。若按第十节实现 `DriverResult`，Stage 3 的编辑 Driver 会再返工一次。这是"必须用户/架构裁定"级别的缺口。
**建议修正**：确立"**生命周期用基类、业务操作走类型化 Driver 接口**"两层协议，不改 8 字段、不新增层：

```rust
// dw-core：只定义接口，不含第三方类型
pub struct RenderRequest { pub page: usize, pub scale: f32, pub rotation_deg: i32 }
pub struct RenderedPage { pub width: u32, pub height: u32, pub rgba: Vec<u8> }

pub trait PdfRenderDriver: IDriver {
    fn open(&self, path: &Path) -> Result<PdfDocHandle, DriverError>;
    fn render_page(&self, doc: &PdfDocHandle, req: &RenderRequest) -> Result<RenderedPage, DriverError>;
}
```

`DriverResult` 整节删除，统一用 `Result<T, DriverError>`；`IExecutable::execute` 在 Driver 上降级为"预热 / 自检"的空实现并在文档中明说。同时必须补一条：**Task 如何从 `&dyn IDriver` 拿到 `&dyn PdfRenderDriver`**（Rust 不支持 trait object 向下转型）。推荐零 unsafe 的手工转型 shim：

```rust
fn as_pdf_render(&self) -> Option<&dyn PdfRenderDriver> { None }   // IDriver 默认方法，实现者覆写
```

备选是 `as_any()` + 向下转型到**具体类型**（会让 Task 依赖 `PdfiumRenderDriver` 具体名，耦合更差，不推荐）。

### 【B-03】P0｜"谁解析 Driver"三处互相矛盾，且选择规则无法执行

**问题**：
1. 三张链路图不一致：第二节 `Task → Driver`；附节 `Task → DriverManager → Driver`；第九节 `Document → Task → DriverManager → Driver`。根因是上游自身有两处表述（`00-B` 第十四节把 DriverManager 画在 Task 与 Driver 之间；`V1.1` 第二条又裁定 Manager 是横切基础设施、不入链），文档 12 作为**实现章**必须裁定，而不是把两种画法都抄一遍。
2. 现有代码已给出第三条路：`task.rs:110-113` 由 `TaskManager::submit` 先 `drivers.get(...)`、再 `task.execute_on(context, driver)` 注入——Task 不认识 DriverManager，Manager 也不在链上，两条冻结表述同时成立。
3. 第十六节选择依据"可用、性能、用户配置"不可执行（见 B-08）；且 `TaskManager` 目前**硬编码** `drivers.get("空驱动")`（`task.rs:111`）——中文名字符串做 id，Stage 2 一加第二个 Driver 就断。
**影响**：Stage 2 至少两个 Driver（渲染 / 文本提取），选择逻辑无处落地；若让 Task 自己 `get`，Task 立刻变成调度者，违反"Task 只是执行器"（`00-B` 第九节）。
**建议修正**：文档写明"**Task 不持有 DriverManager；TaskManager 在提交时解析并注入 Driver**；`Task → Driver` 仍是唯一执行链，DriverManager 是横切解析器"。并补选择 API：

```rust
pub fn select(&self, cap: Capability) -> Option<Arc<dyn IDriver>>;  // 确定性：显式配置 > 注册顺序
```

### 【B-04】P0｜PDFium 工程风险零字，且并发模型与现有 `Mutex<DriverManager>` 直接冲突

**问题**：第七、八节只说"候选 PDFium"，以下五条全部缺失，且都不是理论问题：
1. **分发**：`pdfium.dll` 为 C 库，官方预编译 x64 约 10–20 MB 量级（需实测）。当前绿色版总体积 20 MB（Stage 1 收口报告 2.2），加 DLL 后体积翻倍，"比福昕更轻"的目标需要重新评估。
2. **绑定**：项目 target 是 `x86_64-pc-windows-gnu`（`.cargo/config.toml`），而 PDFium 官方产物是 MSVC 构建、只带 `.lib` 导入库。**不要链接 import lib**，必须运行时 `LoadLibrary`（`libloading` / `pdfium-render` 默认即此模式），否则 GNU 目标链接大概率失败。
3. **`Send`**：`driver.rs:15` 要求 `IDriver: Send`。`pdfium-render` 的 `Pdfium` 句柄默认 `!Send`，需启用其 `thread_safe` feature 或 `unsafe impl Send`（后者在多线程调用下是 UB）。文档必须点名用哪种。
4. **全局状态**：`FPDF_InitLibrary` / `FPDF_DestroyLibrary` 是进程级全局，多实例冲突，必须做引用计数单例；`initialize()` 幂等性要写死。
5. **并发（最要命）**：`ipc.rs:179` 是 `let drivers = lock(&state.driver_manager)`，`get` 返回 `&dyn IDriver` **借用自 manager**，意味着整段渲染期间必须持有 DriverManager 的锁——**所有 Driver 调用被串行化**。而 `08` 第十一节要求 RenderPage1/2/3 并行。此外 `&dyn IDriver` 跨线程需要 `Sync`，当前 trait 只有 `Send`。
**影响**：Stage 2 第一周即卡住；若强行并行，要么死锁，要么 UB。
**建议修正**：文档补"Driver 并发模型"一节，并改两处签名：`IDriver: ... + Send + Sync`；`DriverManager::get/select` 返回 `Arc<dyn IDriver>`（**克隆后立即释放 manager 锁**），Driver 内部用 `Mutex<PdfiumState>` 自管互斥。渲染必须跑在阻塞线程池（`tauri::async_runtime::spawn_blocking`），不得占用 IPC 线程。

### 【B-05】P0｜第十二节 OCR 方案与 `00-D` / `00-C` 硬冲突

**问题**：文档写"第一阶段 Tesseract；未来 PaddleOCR"。`00-D`（最高优先级）是"OCR（MVP）：**Windows OCR（优先）** + Tesseract（可选）；PaddleOCR（以后插件）"，`00-C` 第二节同。文档 12 **漏掉 Windows OCR**，并把 Tesseract 从"可选"提升为"第一阶段"。另附两条 00-C 未列的落地风险，应在文档 12 一并写明：Windows OCR（WinRT `Windows.Media.Ocr`）依赖目标机已安装 `zh-Hans` OCR 语言包，**绿色版无法自带**；Tesseract `chi_sim` 模型为数十 MB 量级，与轻量化冲突。
**影响**：不阻断 Stage 2（OCR 属 Stage 4），但违反最高优先级冻结；且 `dw-ocr/src/lib.rs` 已按"Windows 优先"写好三个 Adapter 占位（`WindowsOcrAdapter` / `TesseractAdapter` / `PaddleOcrAdapter`），文档与代码方向相反。
**建议修正**：改为"Windows OCR（默认，`WindowsOcrAdapter`）→ Tesseract（可选，`TesseractAdapter`）→ PaddleOCR（插件，`PaddleOcrAdapter`）"，并补"无 zh-Hans 语言包时的降级路径"。改动量一段话，但必须改。

### 【B-06】P0｜Stage 2 的"搜索"没有实现来源

**问题**：`Stage-Release` Stage 2 验收含"搜索"，`capability.rs:11` 也已有 `Capability::Search`。但文档第八节把 PDFium 的 `Text Extract` 标为"（可选）"，第七节只字未提文本提取 Driver。
**影响**：Stage 2 验收项无落点。且 `Capability::Search` 目前**没有任何 Document 声明它**（`ipc.rs:167` 只塞了 `Render`），搜索 Task 连 Gate 都过不了。
**建议修正**：文本提取提为 Stage 2 **P0**（`PdfTextDriver::extract_page_text`），并明确 Stage 2 搜索范围仅限**有文本层的 PDF**；扫描件搜索依赖 OCR，属 Stage 4，必须写进 Stage 2 已知限制，否则验收时会被判"搜索不可用"。

### 【B-07】P1｜第五节状态机没有载体，且线性箭头不是合法状态机

**问题**：`Created → Initializing → Ready → Running → Failed → Disposed` 是一条直线，`Failed` 与 `Disposed` 不可能是 `Running` 的唯一后继；且 `driver.rs:55` 的 `DriverManager { registry }` **没有任何状态字段**，状态无处存放。另外"Running"隐含"一个 Driver 同时只服务一个 Task"，与 `08` 第十一节并行渲染冲突。
**建议修正**：状态归 `DriverManager`（Driver 只持有资源），`DriverEntry { driver: Arc<dyn IDriver>, state: DriverState }`；`Running` 改为 `Busy`（引用计数）或直接删除、只保留 `Created/Initializing/Ready/Failed/Disposed`；明确"状态是 `initialize/dispose` 调用的**观测投影**，不是第二套逻辑"，`IHealthCheck::health()` 是运行时探测、与状态机不重叠。

### 【B-08】P1｜第十六节"依据性能"不可执行

**问题**："依据：可用、性能、用户配置"——性能如何测？运行时探测会让启动变慢且结果不确定（同一台机器两次启动可能选不同 Driver），且与"绿色版可离线、行为可预测"冲突。
**建议修正**：改为确定性规则 `显式配置 > 注册顺序 > 拒绝`，性能只作为**离线基准数据**（文档记录，不参与运行时决策）。此条为建议优化，但必须在 Stage 2 前定，否则 Driver 选择行为不可复现。

### 【B-09】P1｜能力双源无合并规则，且 `IDriver::capabilities()` 目前是死代码

**问题**：第六节说"TaskManager 执行前检查 `ExecutionContext.CapabilitySet`"，但 `CapabilitySet` 有两个来源：Document 声明（`document.declared_capabilities`）与 Driver 声明（`IDriver::capabilities()`）。文档未定义谁为准、如何合并。实测 `grep` 全仓：`IDriver::capabilities()` **零调用点**——Driver 能力声明写了但没有任何消费者。
**影响**：Stage 2 会出现"文档声明 `Render`、Gate 通过、但 pdfium Driver 未注册"→ 运行期报错而非准入拒绝，Capability Gate 的唯一准入点价值被架空。
**建议修正**：一句话裁定——**Gate 只认 Document 声明；Driver 能力只用于 `select` 选型；Document 的 `CapabilitySet` 在"打开文档"时由 `格式固有能力 ∩ DriverManager 可用能力` 生成**。这样 Gate 通过即隐含"有 Driver 可实现"，不新增层、不改 8 字段。

### 【B-10】P1｜`DriverError` 只有字符串，无法支撑第十一节的 5 分类

**问题**：第十一节要求 5 类，`error.rs:38-43` 是 `DriverError { driver: String, message: String }`。
**建议修正**：**可以扩展，不会破坏 `PartialEq`**——前提是分类用 `Copy` 枚举、详情仍用 `String`，**不要引入 `source: Box<dyn Error>`**（那会同时破坏 `Clone` / `PartialEq` / `Eq`，而 `DwError` 三者都 derive 了）：

```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum DriverErrorKind { NotSupported, InvalidDocument, PermissionDenied, RuntimeFailure, ResourceMissing }
#[derive(Debug, Clone, PartialEq, Eq)]
pub struct DriverError { pub driver: String, pub kind: DriverErrorKind, pub message: String }
```

并写明 `NotSupported` 的语义边界：B-09 修好后它应当**永不出现**，属"不变量被破坏"信号，需带日志告警。

### 【B-11】P1｜第十七节目录与现有 crate 无映射，`DocumentModel` 复活

**问题**：文档画 `drivers/pdfium/ lopdf/ tesseract/ office/` 四个目录，实际 workspace 是 `dw-pdf` / `dw-ocr` / `dw-office` 三个 crate（`Cargo.toml` members 6 个），且 `dw-core` 里 `driver` 是**单文件** `driver.rs` 而非 `driver/` 目录。另外第十节写"PDFium Object → Driver 内部 → **DocumentModel**"，而 `00-A` P0-4 明确"**不采纳 DocumentModel 命名**"，代码里也只有 `Document` / `DocumentInner`。
**建议修正**：写明映射——`dw-core/src/driver.rs`（接口）+ `dw-pdf`（`PdfiumRenderDriver` / `LopdfEditDriver`）、`dw-ocr`、`dw-office`（实现）；**不新建 `drivers/` 目录、不拆 4 个 crate**（Stage 2–3 拆 crate 只增 Cargo 开销、不提供任何隔离）。`DocumentModel` 全部改为 `Document`。

### 【B-12】P1｜`V1.1` 交给本章的"发现 / 加载 / 隔离"三项全部缺失

**问题**：`V1.1` 最终决定原文是"12：Driver 的**发现、加载、隔离**"。文档 12 第三节只列"注册/初始化/查找/状态/释放"，第十四节只说"第一阶段不开放动态加载，只预留接口"，第十八节又禁 `PluginManager`——于是"谁负责 `.dll` 加载"彻底无人认领，DriverManager 的职责边界是"管理已注册实例"还是"加载器"未定。
**建议修正**：写明三句边界——(1) Stage 1–4 `DriverManager` **只接受已构造的 `Box<dyn IDriver>`，不认识 DLL**；(2) 加载动作属组装层（`dw-desktop` `CoreState`）或独立 crate 的自由函数，不是 Manager；(3) 隔离（崩溃隔离 / ABI 握手）推迟到 Stage 5，并注明 Rust 无稳定 ABI，届时须 `abi_stable` 或 C ABI + 版本号校验——否则 Stage 5 会用 `transmute` 硬上。

### 【B-13】P1｜能力命名与代码不一致

**问题**：第六节 `HasRender` / `HasEditPage` / `HasOCR`；`capability.rs:11-26` 是 `Render / Search / Ocr / Convert / Export / Print / Edit`——**没有 `EditPage`**，只有 `Edit`；`00-B` 第十节写 `HasOCR / HasRender / HasSearch`；`08` 第九节又写 `HasExportWord`。三套命名并存。
**建议修正**：以代码枚举为准（`Capability::Render` 等，不带 `Has` 前缀），文档全章改用 `Capability::Xxx` 形式，并明确"新增变体允许，但需在本章登记 + 同步 `capability.rs`"。页级操作（旋转/删除页）第一阶段归 `Edit`，不新增 `EditPage`。

### 【B-14】P2｜Gate 时机措辞与 `V1.1` 第九条不一致

**问题**：第六节写"TaskManager **执行前**检查"，`V1.1` 第九条是"Task **入队前**"，且"校验为 false：Task 根本不会创建"。而真实顺序是 `Command::build_tasks` 先构造 `Box<dyn Task>`（`task.rs` → `ipc.rs`），再在 `submit` 首行 Gate——**Task 对象已经创建了**。
**建议修正**：文档明确"`build_tasks` 只构造数据结构、不产生任何副作用；Gate 在**入队/首次调用 Driver 之前**执行一次"，并声明"构造 Task 结构体不等于创建 Task"。这不是文字游戏：Stage 2 的 `OpenPdfTask` 若在构造时打开文件，Gate 就真的形同虚设。

### 【B-15】P2｜第九节表述错误

**问题**："`Document → Task → DriverManager → Driver`"——Document 是数据，不调用 Task。
**建议修正**：改为"`Document ←(引用) ExecutionContext → Task → Driver`"，Document 只被读取/`mutate`。

## 三、设计缺口清单（不阻断，但实现时必然要补）

1. **Document 与 Driver 的数据所有权**：`DocumentInner { revision }`（`document.rs:29-32`）没有页树、页数、页尺寸。PDFium 渲染需要文档句柄——是每次 `open(path)` 重开（`metadata.source_path` 可用），还是 Document 缓存 `PdfDocHandle`？**后者会让 Document 持有第三方句柄，与"Document 不持 Driver"冲突**。建议：Stage 2 由 Driver 内部按 `source_path` 维护句柄缓存（LRU），Document 只存页数/页尺寸等纯数据。
2. **位图跨 IPC 传输方案**：一页 2000×1500 RGBA = 12 MB，走 JSON 数组必崩。必须定二进制通道（Tauri 2 `ipc::Response::new(Vec<u8>)` + 前端 `Blob`/`ImageBitmap`），并定缩略图尺寸与缓存位置（`runtime/cache`）。
3. **查看渲染路径二选一**：`00-C` 写"阅读 Viewer：PDF.js"，而 `Stage-Release` Stage 2 与文档第七节都写"PDFium 渲染"。若用户看到的是 PDF.js，则 PDFium 只服务缩略图/打印/OCR 取图——这直接决定 Stage 2 的整体工作量，需要一句话裁定并写入本章。
4. **Driver 配置的落点与 schema**：第十五节给了 JSON 片段，但没说文件在哪（`config/app.json` 已有 `title`/`language`）、字段类型、缺省行为、非法值如何处理。
5. **Driver 生命周期与 Session 的关系**：`09` 第十三节说"Session 只保存 Driver 使用状态"。Driver 是进程级单例还是每 Session 一份？PDFium 句柄若按 Session 隔离，多标签内存会翻倍。
6. **`NullDriver` 的去留**：Stage 1 的 `NullDriver` 声明了 `Capability::Render`，Stage 2 一旦注册真 Driver，Gate 会同时放行两者——`select` 规则必须先于真 Driver 上线。
7. **取消语义**：`IExecutable::cancel(&mut self)` 需 `&mut`，但渲染是在 `&self` 上进行的（B-04 的 `Arc<dyn IDriver>` 更拿不到 `&mut`）。取消必须走 `CancelToken`（`context.rs:22` 现为空结构体，需补 `AtomicBool` + `check()`）。
8. **进度反馈**：`Progress` 同样是空结构体，多页渲染的进度回调无载体。

## 四、与现有代码骨架的对齐建议

| 文件 | 现状 | 建议 |
|------|------|------|
| `dw-core/src/driver.rs` | `IDriver: IExecutable + IHealthCheck + Send`；`get(&self) -> Option<&dyn IDriver>`；`DriverManager{registry}` | 加 `Sync`；`get/select` 返回 `Arc<dyn IDriver>`；`DriverManager` 增加 `entries: HashMap<String, DriverEntry>` + `order: Vec<String>` + `DriverConfig`；`register_empty_driver` 移出（注册应由组装层做） |
| `dw-core/src/task.rs` | `drivers.get("空驱动")` 硬编码中文名 | 改为 `drivers.select(task.required_capability())`，找不到返回 `DwError::Execution("无可用 Driver")`；`execute_on` 保留，但签名扩为可传 request |
| `dw-core/src/error.rs` | `DriverError{driver, message}` | 加 `kind: DriverErrorKind`（保持 `Clone/PartialEq/Eq`） |
| `dw-core/src/capability.rs` | 7 变体，`Edit` 无页级粒度 | 不动枚举；新增 `CapabilitySet::intersect(&self, other) -> CapabilitySet` 供 B-09 的"格式能力 ∩ Driver 能力"使用 |
| `dw-core/src/context.rs` | `CancelToken{}` / `Progress{}` 空结构体 | 补 `CancelToken{ flag: AtomicBool }` + `is_cancelled()`；`Progress{ current, total }`——**不加字段**，只填内容，8 字段冻结不破 |
| `dw-pdf/src/lib.rs` | 单个 `PdfDriver` + 两个空 Adapter | 拆为 `PdfiumRenderDriver`（impl `PdfRenderDriver`）与 `LopdfEditDriver`（impl `PdfEditDriver`），与第七节的三分职责对齐；`PdfMetadataDriver` 可并入 Edit |
| `apps/dw-desktop/src/ipc.rs` | `let drivers = lock(&state.driver_manager)` 全程持锁 | 改为 `let driver = { lock(&state.driver_manager).select(cap)? };` 后立刻释放锁，再 `spawn_blocking` 执行 |

核心签名建议（一次性写进文档第四节，作为 Stage 2 契约）：

```rust
pub trait IDriver: IExecutable + IHealthCheck + Send + Sync {
    fn name(&self) -> &str;
    fn capabilities(&self) -> CapabilitySet;
    fn as_pdf_render(&self) -> Option<&dyn PdfRenderDriver> { None }
    fn as_pdf_edit(&self) -> Option<&dyn PdfEditDriver> { None }
}

pub trait PdfRenderDriver: IDriver {
    fn open(&self, path: &Path) -> Result<PdfDocHandle, DriverError>;
    fn render_page(&self, doc: &PdfDocHandle, req: &RenderRequest) -> Result<RenderedPage, DriverError>;
    fn close(&self, doc: PdfDocHandle);
}
```

## 六、结论

文档 12 的**概念判断全部正确，工程契约几乎全部缺失**。它守住了六条红线，却把 Driver 最核心的三件事（怎么被调用、谁来选、能力以谁为准）留成空白，外加一处与最高优先级冻结（`00-D` OCR）的正面冲突。定性为"**补齐型返工**"而非"推翻型返工"：六个 P0 中有四个是补签名/补裁定，B-05 是一段话，真正需要新增工作量的只有 PDFium spike 一项。

建议路径：**先改文档 12（P0 六条 + B-09/B-11/B-13 顺带），再做 PDFium spike，两者都过再开 Stage 2 的第一行代码。** 顺序不能反——spike 的结论会反过来决定第四节签名里 `PdfDocHandle` 的形态（是否带生命周期、是否可跨线程）。

另需提请用户注意一条超出本章范围的事实：`V1.1` 已宣布"架构阶段结束、08 起全部为实现设计"，但文档 12 仍有六处需要**架构级裁定**（调用协议、Driver 解析者、能力双源、并发模型、查看渲染路径、插件边界）。这说明"实现设计"阶段仍会产生架构决策——建议沿用 11.1 的形式，出《12.1 Driver 实现补充决议》单独裁定，避免第 12 章被反复改写。
