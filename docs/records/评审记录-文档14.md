## P0-1 / P0-2：打开文档的「鸡生蛋」——**同源，一条裁定解决**

### 事实链（四份规范互相咬死）

| # | 出处 | 原文 |
|---|---|---|
| 1 | `01` §4.3 | Context 组装伪代码：`let document = session.documents.get(document_id)?;` —— **组装 Context 的前提是 Document 已存在** |
| 2 | `01` §4.3 第 2 条 | 「Context **不感知 `DocumentStore`**，只持解析后的 `&Document`」 |
| 3 | `01` §4.3 | `capability_set: document.declared_capabilities.clone()` |
| 4 | `02` §3.2 | Gate 校验依据是 `ctx.capability_set` |
| 5 | `02` §2.3 | `OpenDocumentTask` 的 `required_capability` = `Render` |
| 6 | `03` §5.3 | `fn read_metadata(&self, document: &Document)` —— **读元数据也要先有 Document** |

### 推论

打开 PDF 时，Document 还不存在，于是：

- **P0-1**：Context 组装不出来（第 1、2 条）→ `OpenDocumentTask` 无法 `execute_on`。
- **P0-2**：`capability_set` 来自 `document.declared_capabilities`，而文档没加载过、能力集为空 → Gate 判 `false` → **必然 `TaskRejected`** → **永远打不开第一个 PDF**。

文档 14 §七 写的「Task 执行：验证文件 → 读取Metadata → **创建Document → 加入DocumentStore**」在现行规范下**不可能实现**——Task 拿到 Context 时 Document 必须已存在，Task 不能再创建它。`03` §5.3 的 `read_metadata(&self, document: &Document)` 同样要求 Document 先存在。

### 建议解法（不需要改任何冻结条款）

把「打开」拆成**注册**与**加载**两段，注册不入执行链：

```
① 组装层（CoreState）收到 open(path)
     → 识别格式（.pdf）
     → DocumentStore::create(kind, declared_capabilities)   ← 纯数据分配，不是业务操作
     → 得到 document_id（DocumentState = Created）
② 组装 Context（此时 document 已存在，8 字段照旧）
③ OpenDocumentCommand { path } → build_tasks() → Capability Gate → ExecutionGraph
     → OpenDocumentTask { path } → Gate(Render) ✓ 通过
     → PdfDriver::read_metadata(&document) → document.mutate() 填元数据
     → DocumentState: Created → Loading → Ready
④ UI 拿到 document_id，PDF.js 自己加载字节渲染
```

依据：
- `01` §5.3 状态机本来就有 `Created / Loading / Ready`，说明「先建空文档再加载」是设计内路径。
- `02` §2.4 允许 `declared_capabilities` 由能力矩阵填入（矩阵只决定声明内容，不产生分支代码）。
- `DocumentStore::create()` 是数据分配，不是业务操作，放在组装层不违反 `00` §1.3。

**需要你确认的只有一句**：`DocumentStore::create()` 由**组装层在 submit 之前**调用，算「数据分配」而非「业务操作」——认可这一点，P0-1 与 P0-2 同时解决，规范一个字不用改。

## P0-3：`Open` 到底入不入 History —— 需裁定

### 事实链

| # | 出处 | 原文 |
|---|---|---|
| 1 | `02` §1.1 | `trait Command` 强制 `fn undo(&mut self, ctx) -> Result<(), DwError>` 与 `redo()` |
| 2 | `02` §1.2 | `CommandKind` 已有 `Open` 变体 |
| 3 | `02` §1.5 第 4 步 | 全部 Task 成功后 `history.record(CommandRecord)` |
| 4 | `00` §5.3 | 「Undo / Redo 只应用或回滚 Diff」 |
| 5 | `00` §5 | 「`Diff` 由 **Task 生成**」；打开文档不改内容 → 无 Diff |

### 矛盾

按现行条文，打开 PDF 会：① 被记进 History；② 必须实现 `undo()`。但打开没有 Diff，`undo(open)` 无 Diff 可应用 → 变成空操作，`cursor` 却照样回退。**结果是 Undo 栈里出现一条按了没反应的记录**，用户按 Ctrl+Z 一次什么都没发生，这是明确的可用性缺陷，也让 History 的语义失真。

### 两个方向（请择一）

| 方案 | 做法 | 代价 |
|---|---|---|
| **A（建议）** | 明确「只有**改变文档内容**的 Command 才 `record` 到 History；`Open` / `Close` / 视图类 Command 只执行、不记录」。`Command` 增加 `fn records_history(&self) -> bool { true }`，`Open` 返回 `false` | 需在 `00` §5 补一句边界，属 R1.1（补语义边界，不动 Undo 模型结构） |
| B | 保留记录，`undo(open)` 定义为「关闭该文档」 | 用户按一次 Undo 会关掉文档，与直觉相反；且关闭属另一条 Command，造成语义重叠 |

选 A 之后，文档 14 §六 的 `OpenDocumentCommand` 就是「有 Command、有 Task、走 Gate、但不进 History」，`undo()` 实现为 `Ok(())` 并在注释写明「打开不产生内容变更，不入 History」。
