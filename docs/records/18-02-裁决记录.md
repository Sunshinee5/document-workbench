# 18-02《PDF Object Parser》架构裁决记录

日期：2026年11月25日
性质：过程记录，仅溯源；规范效力以 `docs/spec/08-PDF-Object-Parser-R1.md` 为准（第一章 Architecture Decisions）。

---

## AD-01 · ObjectMapper 不属于 Parser（用户裁决，采用）

保持 18-01 冻结结果，不修改。18-02 初稿把 ObjectMapper 画在 PDFParser 内部是误导。

正确关系：`lopdf::Document → PDFParser → PDF Intermediate → ObjectMapper → Object Tree`。
实现上 Parser 可调用 ObjectMapper，但**所有权不属于 Parser**。

原因：ObjectMapper 后续需服务 Save / Incremental Save / OCR / AI / Annotation / Form / Content Rewrite，Parser 只是调用者。

冻结：ObjectMapper 是 Editor Engine 唯一对象映射组件，由多 Feature 共用；Parser 不拥有，只依赖其接口。

## AD-02 · UnknownObject 属于统一 Object Model（用户裁决，采用）

扩展 18-01 `ObjectKind`，不建立第二套对象体系。禁止 Parser Object / Editor Object 两套模型。

```
enum ObjectKind { Text, Image, Path, Annotation, Form, Unknown }
UnknownObject { operator, operands, stream_ref }
ObjectPayload::Unknown(UnknownObject)   // payload 是 07 已冻结字段名，不改名
```

不是 Parser 内部类型。冻结：UnknownObject 是 `07` 合法对象类型，由 Parser 创建、ObjectMapper 映射、Save Pipeline 原样保留。

## AD-03 · Parser 不生成业务对象（用户新增裁决，最重要）

Parser 只解析 PDF，产出中间节点；真正的 Editor Object 由 ObjectMapper 创建：

```
lopdf Object → Parser → Intermediate Node → ObjectMapper → Editor Object
```

好处：以后换 MuPDF / PDFium 只需替换 Parser，Object Model 不用改。

冻结：Parser 输出 `PDF Intermediate`，不直接产出 `07` 定义的 Editor Object；ObjectMapper 是唯一映射组件。

## 落地裁决（主理人补充）

| # | 议题 | 裁决 |
|---|---|---|
| 4 | ObjectTree 位置 | 领域类型放 `dw-core/src/object_tree.rs`；解析缓存状态放 `dw-pdf` |
| 5 | Viewer / PDF.js | 不违反唯一解析入口：查看渲染平行路径，不构建编辑对象 |
| 6 | MetadataParser | 复用 17 的 `LopdfAdapter::read_metadata()`，禁止第二套解析 |
| 7 | ObjectId 稳定 | `(xref, gen, stream 序号, operator 下标)` 确定性派生，禁止随机/UUID/地址 |
| 8 | PageId 稳定 | lopdf 页树原始页码（1 起） |
| 9 | Lazy / Cache | ObjectTree 持 page_cache + parsed_pages；Parser 提供 parse_first_page/parse_page/invalidate_page |
| 10 | 后台线程 | Parser 及子组件 Send + Sync；不实现线程池 |
| 11 | 边界 | 不做 HitTest / Selection / Text Editing / Save / OCR / AI / UI / IPC |
