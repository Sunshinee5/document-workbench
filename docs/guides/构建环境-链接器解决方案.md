# 构建环境：MSVC 链接器缺失的解决方案

整理时间：2026年11月22日
状态：已解决。`cargo test -p dw-core --target x86_64-pc-windows-gnu` 实测 2/2 通过；`cargo +stable-x86_64-pc-windows-gnu check -p dw-desktop` 实测 EXIT 0，零警告。

## 问题

QA 验证骨架时发现：本机无 MSVC C++ 链接器（link.exe），`cargo check` 能过（不链接），但 `cargo test`/`cargo build` 在链接阶段失败。原方案是装 Visual Studio BuildTools，但下载源 `download.visualstudio.microsoft.com` 在当前网络下完全不通。

## 排查结论（多方法实测）

| 方法 | 结果 | 原因 |
|------|------|------|
| curl 直连/代理下载 vs_BuildTools.exe | 失败 | download.visualstudio.microsoft.com 域名断流 |
| winget install | 失败 | msstore 源证书不匹配（0x8a15005e） |
| bootstrapper 安装 | 失败 | ①代理变量 HTTPS_PROXY 与 https_proxy 重复导致 .NET Hashtable 崩溃；②修复后 setup.exe 能启动但组件下载仍卡在 download 域名 |
| PowerShell WinHTTP 下 aka.ms | **成功**（4.47MB） | WinHTTP 通道对 aka.ms 可达，但对 download 域名也超时 |
| 系统已有 link.exe / CRT 库 | 无 | 只有 Git Bash 的 GNU link，无 MSVC CRT |

## 最终方案：LLVM-MinGW + Rust GNU target（已完成）

不依赖 MSVC，改用 Rust 官方支持的 GNU 工具链。全部下载物放在 D 盘。

### 已安装组件

1. **LLVM-MinGW 工具链**（192MB）
   - 来源：NuGet 包 `Sushi.NativeToolchain.LlvmMingw.WinX64` 20260616.0.0（NuGet 域名可达）
   - 下载：`D:\Downloads\VSBuildTools\sushi.nativetoolchain.llvmmingw.winx64.20260616.0.0.nupkg`
   - 解压：`D:\Downloads\VSBuildTools\llvm-mingw\toolchain\`
   - 关键程序：`bin\gcc.exe`（clang 22.1.8）、`bin\ar.exe`
2. **Rust GNU target**
   - `rustup target add x86_64-pc-windows-gnu`（静态 rust-lang.org 与清华镜像均可达）
3. **libgcc 兼容库**（本机现场生成）
   - Rust GNU target 默认链接参数含 `-lgcc_eh -lgcc`，但 LLVM-MinGW 用 libunwind 替代
   - 在 `llvm-mingw\toolchain\x86_64-w64-mingw32\lib\` 下：
     - 复制 `libunwind.a` → `libgcc_eh.a`
     - 用 `ar.exe rcs libgcc.a` 创建空 archive（compiler_builtins 已提供内建函数）
4. **项目构建配置**：`.cargo/config.toml`（已提交到项目）
   - 指定 `[target.x86_64-pc-windows-gnu]` 的 linker/ar 指向上述 MinGW 工具
   - 不影响默认 MSVC target

## dw-desktop / Tauri 验证（GNU host 工具链）

### 新增问题：build script 走 host MSVC target

Stage 1 验证 `cargo check -p dw-desktop --target x86_64-pc-windows-gnu` 时，失败不在业务源码，而在第三方依赖（`proc-macro2`、`quote`、`serde`、`thiserror`、`icu_normalizer_data` 等）的 **build script**：Cargo 总是用 **host target** 编译并执行 build script，默认 host 为 `x86_64-pc-windows-msvc`，链接需要 MSVC `link.exe` 与 Windows SDK（`kernel32.lib` 等），本机两者都没有，报 `linking with link.exe failed` / `you may need to install Visual Studio build tools`。

无效尝试（留作教训）：

- `-Ztarget-applies-to-host`（含 `RUSTC_BOOTSTRAP=1`、`CARGO_UNSTABLE_TARGET_APPLIES_TO_HOST`）：build script 仍走 MSVC。
- `RUSTFLAGS="--target x86_64-pc-windows-gnu"` 配合命令行 `--target`：`--target given more than once`。
- 仅用 RUSTFLAGS 指定 target：build script 转 GNU 成功，但 proc-macro crate 失配（`can't find crate for serde_derive` 等）。
- 只给默认工具链加 GNU target：能解决 `dw-core`，解决不了 Tauri 依赖链。

### 解法：GNU host 工具链 + 合法图标

1. **安装 GNU host 工具链**（不是只加 target）：`rustup toolchain install stable-x86_64-pc-windows-gnu --target x86_64-pc-windows-gnu`。关键是换掉整个 host 工具链，让 build script 用 GNU std 编译，与 target ABI 统一，彻底绕开 MSVC `link.exe`。
2. **合法 Windows 图标**：`apps/dw-desktop/icons/icon.ico` 必须存在且为合法 ICO（16×16、32bpp 最小可用）。Tauri 在 Windows 上用它生成资源文件（RC），缺失或非法会在资源编译阶段失败。

### 验证命令

```bash
cd /d/DocumentWorkbench
export PATH="/d/Downloads/VSBuildTools/llvm-mingw/toolchain/bin:$PATH"
export RUSTUP_HOME="/c/Users/Administrator/.rustup"
export CARGO_HOME="/c/Users/Administrator/.cargo"
cargo +stable-x86_64-pc-windows-gnu check -p dw-desktop
```

实测 EXIT 0，Tauri 全依赖链编译通过、零警告。

### 适用范围（分界）—— 2026年11月22日 更新

**分界不再是「零依赖 / 带依赖」，而是「有没有 host build script」。**

- 文档 11 修正后 `dw-core` 引入了 `serde` / `serde_json`，编译期要为 `proc-macro2` / `quote` 等 crate 运行 **host build script**，同样需要 `link.exe` → **`dw-core` 现在也必须用 GNU host 工具链**。
- 结论：本项目**全部 Rust 命令统一使用 `cargo +stable-x86_64-pc-windows-gnu`**，不再区分 crate。
- 走错工具链的症状：EXIT 101，错误全部是 `linking with link.exe failed` / `link: extra operand`（Git Bash 的 coreutils `/usr/bin/link.exe` 抢占同名命令），而 `E*` 编译错误计数为 **0**。看到这个特征就是工具链问题，不是代码问题，不要浪费时间改代码。

## 注意事项

- 本项目所有 Rust 命令（check / test / build）统一加 `+stable-x86_64-pc-windows-gnu`；裸 `cargo` 在引入 serde 后不再适用。
- 需要实际链接（test/build 出 exe）时，同样走 GNU host 命令。
- 工具链安装在 D 盘，未占用 C 盘；NuGet 下载物保留在 `D:\Downloads\VSBuildTools\` 供复用。
- 若换机或工具链路径变化，改 `.cargo/config.toml` 的 linker/ar 路径即可。
